Strategy carve-out — architecture, hand-over boundary and acceptance

This document defines a credible standalone hand-over of the contracted strategy: the components transferred and the form each takes, the runtime path through them, the interfaces at which platform services are substituted, and the acceptance test that says the hand-over is complete. It is written to be planned and contracted against.

Working principle

The hand-over transfers a strategy that a competent engineering team can make operational — not a replica of the operating platform built around strategies. The boundary is made explicit in code: strategy decision logic is portable, and every point where the platform normally supplies a capability appears as a typed interface rather than as something silently absent.

01

What "runnable" means — the acceptance bar

"Runnable" is defined narrowly and deliberately. It means a team can take the package, supply credentials and infrastructure, complete a clearly identified set of platform substitutions, and run the contracted strategy against the agreed venues and instruments. It does not mean inheriting an operating model.

In scopeStrategy decision logic, static universe and configuration, thin venue connectivity, basic execution, a local test harness
SubstitutedTen platform capabilities, each behind a typed interface with a local or static implementation supplied
Out of scopeExecution algorithms, dynamic universe and allocation, reconciliation and attribution, version governance, multi-client machinery
The capability boundary, and the two paths this document sits between

Governance and compliance trail interface No version governance, approval trail, per-client or share-class rules, or centralised audit machinery

The two paths

This document specifies one of two paths. They differ as follows; the election point and support period are defined in the service-level agreement rather than here.

  • Odum-operated. The strategy runs on the platform as a client-isolated deployment. POD holds read access to its own positions, runs, attribution and strategy decision records, queryable remotely. The ten interfaces in §04 resolve to maintained services.
  • Self-operated. The package in §02 transfers. The ten interfaces resolve to local or static implementations, and §07 lists the standing operational functions that come with running it.
Status of this specification

The eleven packages in §02 are a proposed extraction structure, not existing repositories. The strategy, adapter and contract code they contain is production code running today; the packaging, the interface layer and the local implementations are scoped extraction work. §06 is the acceptance test that would close it.

Two notes on the source column. First, no package is a directory copy: each is an import closure taken over the repository tier graph, which is computable exactly because imports only ever point downward through that graph — so the package is reproducible from a commit rather than assembled by hand. Second, the count of components is larger than the count of source repositories, because the extraction splits along capability lines rather than along our internal repository boundaries. §09 maps it the other way, from the estate to the package.

03

Runtime path through the carved system

The runtime path is short and auditable by design. Seven steps from a venue event to a persisted decision, each owned by exactly one component.

Seven stepsEvent, normalise, decide, guard, order intent, place, persist — one owner each
One decision pointAll strategy logic sits in step 3; the components either side are transport and safety
AuditableA reviewer can follow one tick end to end without entering platform code
The seven steps, their owners, and where the platform normally intervenes

The design intent is that every place where the platform normally adds capability is an explicit interface boundary rather than something embedded invisibly in the carved code. That gives a clean engineering choice at each seam: implement the dependency, or resolve it to a maintained service.

Named requirement — funding-rate reader

The staked-basis archetype reads a funding-rate feature. On the platform that value is produced by the market-data path and the features pipeline. The only direct-from-venue implementation currently outside that path sits in a test repository, which is not in the transferring set. A self-operated deployment therefore needs a production funding reader per venue behind FeatureProvider as a first-order item. We are productionising these readers into the licensed set; until that lands, treat it as scoped extraction work in either direction.

05

Configuration and parameter snapshot

At the hand-over point the package receives a configuration snapshot. Several values that the configuration format presents as constants are, on the platform, outputs of services that recompute them — and the file format does not distinguish the two cases, so it is stated here explicitly.

TransferredOne parameter set, a documented schema with validation constraints, the covered universe, and a version identifier binding source, config and fixtures
Not transferredParameter history, the search space, the optimisation pipeline, auto-tuning, alternate variants, research notebooks
ConsequenceThe set is correct for the conditions it was fitted against and does not re-derive itself
What the snapshot contains, and which inputs are constants here but services on the platform

The snapshot comprises exactly five things:

  • One parameter set, appropriate to the agreed universe at the agreed version and date.
  • A human-readable schema describing every strategy parameter and its validation constraints.
  • The exact venue and instrument universe covered by the acceptance test in §06.
  • A version identifier tying source, configuration and test fixtures together.
  • The replay fixtures the acceptance test runs against.

It does not include the parameter history, the search space, the optimisation pipeline, an auto-tuning loop, alternate strategy variants, or research notebooks, unless separately agreed.

Constants here, services there Capability boundary — mechanism detail is out of scope for this document
InputIn the packageOn the platform
Instrument universe A fixed list in configuration UniverseService — selected from cross-venue rate data and re-evaluated on a schedule
Structure per venue One structure per venue, chosen once Selected per venue against current collateral acceptance and rate conditions, within each venue's rules
Capital allocation One allocation, changed by editing configuration PortfolioRiskService — allocated across strategies, venues and versions
Hedge and sizing parameters Fixed values, valid for the conditions they were fitted against Re-fitted on a research cadence, version-controlled and promoted rather than edited in place

Decision provenance Application logs and the local ledgers Every instruction and event carries its build, version, configuration hash and attestations, so a run replays deterministically from its manifest

Whether a fixed set drifts materially over a given horizon is a question about the strategy's environment rather than about the software, and it is measurable directly — compare a frozen set's behaviour against a re-derived one over the same window. It is raised here only because it is not visible from reading the package.

Hand-over acceptance criteria

The hand-over is complete when these nine conditions hold. They are written to be executed and signed off rather than agreed in principle, and the last one is the most important.

Nine conditionsBuild, connectivity, market state, decision determinism, orders, safety, configuration, observability, documentation
Determinism is testableSupplied replay fixtures must produce identical decisions on your infrastructure
Condition 9 is the real testYour team can enumerate every external dependency it must replace to operate independently
The nine acceptance conditions
Acceptance test Executed jointly during the support period defined in the SLA
#AreaAcceptance condition
01BuildThe package set builds from a clean checkout using documented dependencies, on your infrastructure, without access to our estate
02ConnectivityConnects to each agreed venue in sandbox or an agreed safe production mode, authenticating with your credentials
03Market stateConsumes the required market and account events and constructs the minimal strategy state from them
04Decision logicProduces deterministic, identical strategy decisions for the supplied replay fixtures
05OrdersExpresses strategy order intents through the basic execution implementation, including the multi-leg sequence
06SafetyLocal hard limits and the kill-switch path are demonstrated to fire under induced conditions
07ConfigurationRuns on the frozen agreed configuration, and fails loudly and clearly on an invalid one
08ObservabilityProduces local logs and metrics sufficient for your team to debug the strategy process unaided
09DocumentationYour engineering team can enumerate every external dependency it must replace to operate independently — the ten contracts in §04 and the nine functions in §07

Condition 9 carries the most weight because it is the one that prevents a hand-over from looking complete and failing later. A package that builds, connects and trades in a sandbox but leaves its substitution list implicit is the failure mode worth designing against, which is why the interface seam exists as a shipped artefact rather than as an appendix to a document.

One structural note for planning. Of the nine, seven are insensitive to how many strategies they serve: a release pipeline, a monitoring estate and an on-call rota cost substantially the same for one strategy as for several. That is why the operational estate rather than the strategy code tends to dominate the cost of a self-run deployment — and it is the part most usefully estimated against your own infrastructure rather than from this document.

Regulated venues as the worked discontinuity

A regulated futures venue is not another venue with a different symbol format. It brings a different protocol family rather than REST and WebSocket, a clearing relationship to establish and maintain, regulatory reporting obligations, a margin model computed by the clearing house rather than from a collateral haircut, and cash settlement on a settlement cycle rather than a wallet transfer. Each touches a different layer.

On the platform, part of that groundwork exists: a broker-gateway service managing the long-lived connection to a regulated broker, a TradFi market-data path with its own vendor integration and instrument definitions for futures and options, a pricing service already computing greeks and carry-family rates, and a delta-one feature family. Adding a regulated venue is an integration project with a compliance workstream beside it. Self-operated, the same ambition is a futures-capable trading system built next to the crypto one, then reconciled with it.

On the shared spine

Every strategy on the platform emits the same instruction contract and writes the same ledgers, so an improvement to execution, reconciliation or a venue integration applies to all of them. A transferred package is a snapshot at a commit and does not receive later platform work — a property of any code transfer, stated here so it is priced rather than discovered.
