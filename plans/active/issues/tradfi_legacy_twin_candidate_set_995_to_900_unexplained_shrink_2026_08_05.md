# TradFi — legacy-twin candidate set 995 → 900 unexplained shrink

## What I found

The tradfi legacy-twin delete candidate population is cited as **995** actionable class-B rows throughout
`/plans/active/tradfi_legacy_twin_bucket_deletes_signoff_2026_07_24.md` (the "Where the dry-run evidence already lives"
section and the still-open delete todo both scope to "the 995 tradfi legacy-B candidate rows"), sourced from the
2026-07-10 full orphan sweep (`A_canonical_manifested=2,594,017 · B_legacy_duplicate=995 · …` over 10,584,946 objects).

The 2026-07-30 dry-run of `cleanup_legacy_twins.py --asset-group tradfi` loaded **900** rows from the same report URI
(`gs://market-data-tick-tradfi-prd-central-element-323112/_index/audit/orphan_sweep_tradfi.parquet`) — **95 fewer**,
with no explanation.

The executing session (2026-07-30, batch1 REVIEW todo) recorded the discrepancy honestly ("the report has evidently
shrunk by 95 rows in the interim, not re-investigated here") and moved on. No one has investigated since, and no doc in
the corpus explains the delta.

The report file's GCS modification date is **2026-07-30T04:08:14Z** — it was regenerated after the original 2026-07-10
sweep. The `cleanup_legacy_twins.py` loader does NOT filter beyond `obj_class == "B_legacy_duplicate"` (verified by code
read, 2026-08-05), so the 900 count faithfully reflects the report content. The shrink is in the **report data**, not in
the loader.

## Why it matters

This report IS the delete's candidate list. An unexplained mutation of the candidate list is an unexplained mutation of
a delete's blast radius — 95 rows that WERE flagged as class-B legacy duplicates in the 2026-07-10 sweep are no longer
flagged in the 2026-07-30 sweep, and nobody knows why. If 95 twins were folded/migrated/deleted by another pass, that's
fine — but it needs to be recorded. If the report silently drops malformed rows, that could mask real duplicates. If two
different report generations are being conflated, the delete scope is ambiguous.

## Candidate explanations

None verified. Candidates, from the finalize plan's todo 2:

1. **(a)** The report was legitimately regenerated by a later orphan sweep with a corrected taxonomy, and 95 objects
   were reclassified (e.g. B→C/infra, or B→D/junk, or removed from scope).
2. **(b)** 95 twins were folded/migrated/deleted by another pass between 2026-07-10 and 2026-07-30, and the regenerated
   report correctly reflects that.
3. **(c)** The orphan sweep loader silently drops malformed/unparseable rows (95 of 995 ≈ 9.5% would be a significant
   data-quality signal).
4. **(d)** Two different report generations are being conflated — the 995 from a 2026-07-10 sweep and the 900 from a
   2026-07-30 sweep are genuinely different data, and the 2026-07-30 sweep is the one that should be cited everywhere.

## Recommended decision

Run a fresh orphan sweep for tradfi and compare the class-B population against both the 995 (2026-07-10) and 900
(2026-07-30) baselines. The sweep itself is read-only and cheap. Once the current population is known:

- If it's ~900: the 995 figure is stale and must be corrected everywhere it appears in
  `tradfi_legacy_twin_bucket_deletes_signoff_2026_07_24.md`.
- If it's ~995: the 2026-07-30 dry-run had a data issue and the 995 figure is still authoritative.
- Either way, the root cause of the delta must be documented so nobody re-investigates this.
