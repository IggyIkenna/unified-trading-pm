## What I found

`plans/active/prediction_satellite_ao_dispatch_batch6_2026_07_29.md` is 1001 lines — 1 line over plan-hygiene's hard cap
(500 soft / 1000 hard, `check_line_caps.sh`, no exemptions per the 2026-07-24 ruling). This blocks `prek`'s
`plan-hygiene` hook from allowing ANY commit that stages this file, including trivial/mechanical ones — confirmed live:
a pure whitespace-only prettier-reformat restore (verified via `git diff -w` returning empty) was rejected with
`HARD prediction_satellite_ao_dispatch_batch6_2026_07_29.md 1001L todos=21`.

Separately, this file's own prek-hook run left an orphaned prettier-reformat patch
(`/home/ubuntu/.cache/prek/patches/1786783032488-621207.patch`, generated by MY session's `safe-doc-push.sh` run on a
DIFFERENT doc) that could not be committed for the same reason. The patch content (whitespace/indentation only, no
textual change) was reverted rather than left dangling dirty in a shared slot's tree; nothing was lost that isn't also
recoverable by re-running prettier on the file once the cap is fixed.

## Why it matters

Any future agent that needs to touch this file for a genuine reason (flip a todo, append a Progress Log entry, or land a
routine formatting fix) will hit the same hard rejection until the file is split. This is exactly the failure mode
`check_line_caps.sh` and the 2026-07-24 no-exemptions ruling are meant to prevent from persisting — a stuck-over-cap
plan silently blocks its own maintenance.

## Recommended decision

Split the plan per the existing `depends_on`/phase-chain convention (`plans/active/task_template.md` §"partial
parallelism isn't expressible in one plan → SPLIT"), keeping the sibling `_finalize.md` plan's gating intact. This is a
mechanical split (move content, preserve todo IDs/checkboxes, keep both halves under 1000 lines) — outcome is
determinable by the worker alone, no design judgment needed.
