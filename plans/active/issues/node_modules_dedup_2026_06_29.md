# Node `node_modules` dedup — uv-equivalent for node repos?

> **⚠️ DIAGNOSED, NOT PROVEN — REVIEW-GATED. Do NOT implement from this doc yet.** Unlike the uv fix
> (`slot_venv_duplication_disk_pressure_2026_06_29.md`), which was proven end-to-end (clean-room + real-slot inode
> tests) BEFORE shipping, this finding is from symptoms only. The proposed resolution is a **hypothesis** with an
> unresolved root cause and a real blast radius (every node repo's install + possibly CI). It is written specifically so
> a second agent can cross-check it before any change. `assigned_vm: NA`.
>
> **Author honesty note:** during diagnosis I made a measurement error worth flagging — I first sampled a TOP-LEVEL
> `node_modules/<pkg>` entry (got `links=1`) and wrongly concluded "pnpm dedup is broken." The correct target is the
> file UNDER `node_modules/.pnpm/<pkg>@<ver>/...` (pnpm's real store-hardlink target). Re-measuring there changed the
> conclusion. Any reviewer must measure the `.pnpm` path, not the top-level symlink.
>
> **🔎 REVIEWED 2026-06-29** (second agent, claude-opus-4-8): the honesty + proof discipline here is good and the core
> instinct (pnpm store = the uv-cache equivalent) is right. But a grounded re-measurement on the dev host **changes
> several premises**: (1) on this host pnpm slots **already dedupe** (store is workspace-local + same-FS, slot `.pnpm`
> files are `links=2` — NOT the standalone copies the VM showed), so the cross-FS worry for the dev host is **moot** and
> the reclaimable size is **overstated** by naive `du`; (2) Unknown #1 is **host-specific** and cannot be closed without
> ONE measurement taken _on the orchestrator VM_; (3) two findings the doc missed — the codex SSOT **contradicts** the
> gitignore "symlink to shared install" comment (no such mechanism exists in code), and the UI repo commits **both**
> `package-lock.json` AND `pnpm-lock.yaml` (ambiguous package manager, the likely real cause of the npm-vs-pnpm split).
> Full analysis + corrected recommendations in **§ Reviewing-agent findings**. Net: **resolution A done right, reject B,
> schedule C as its own plan** — and do the VM measurement before any change.

## Question being answered

The uv fix deduped Python venvs fleet-wide. Is there an equivalent for the **node/TS repos**
(`unified-trading-system-ui`, `deployment-ui`, `agent-orchestrator/dashboard`, `unified-trading-pm/presentations`),
whose `node_modules` are replicated per slot? And — given the blast radius — is the fix actually safe and worth it?

## What's CONFIRMED (measured)

- **Package managers:** `unified-trading-system-ui` → **pnpm**; `deployment-ui`, `agent-orchestrator/dashboard`,
  `unified-trading-pm/presentations` → **npm** (`package-lock.json`).
- **Total `node_modules` footprint:** **11 GB** (root + slots). Bulk = `unified-trading-system-ui` (~2.3 GB root +
  ~1.1–1.3 GB × ~6 slots ≈ 9 GB). `deployment-ui` ~333 MB × N.
- **pnpm store:** `/home/ubuntu/.local/share/pnpm/store/v3`, **1.2 GB**, on `/dev/root` (same FS as the workspace HERE).
  `package-import-method` = **undefined** (pnpm default `auto`), `store-dir` = **undefined** (default `$HOME` location).
  No committed `.npmrc` in the UI repo.
- **pnpm IS hardlinking to its store — within a repo.** The real file
  `node_modules/.pnpm/lightningcss-linux-x64-musl@1.32.0/.../lightningcss.linux-x64-musl.node` in the ROOT repo is
  `inode=6919311 links=2` (store + node_modules). So pnpm dedup is NOT globally "off" the way uv was.
- **But slots hold STANDALONE copies, not store-hardlinks.** The same `.pnpm` file across slots:

  ```
  root   inode=6919311  links=2   ← hardlinked to store
  slot4  inode=9512795  links=1   ← standalone copy (no store link, no cross-slot share)
  slot5  inode=11797903 links=1   ← standalone copy
  slot6  inode=8240007  links=1   ← standalone copy
  ```

  Different inodes + `links=1` = each slot's `node_modules` is its own physical copy. So there IS real cross-slot
  duplication for the pnpm repo (~6–7 GB plausible upper bound if collapsed to one shared store).

- **npm has no cross-project dedup at all.** npm's cache (`~/.npm/_cacache`) stores download _tarballs_, not unpacked
  packages — every `npm install` re-extracts full copies into each project's `node_modules`. (`vm-disk-guard` wipes
  `_cacache`, which only affects re-download time, not the per-project duplication.)
- **Tooling present:** `pnpm` (`/usr/bin/pnpm`) and `hardlink` (util-linux, `/usr/bin/hardlink`) are installed.

## What's UNKNOWN (the crux — a reviewer must resolve before any fix)

1. **Why do slot installs COPY (`links=1`) while the root install HARDLINKS (`links=2`), on the same filesystem with the
   same `$HOME` store available?** This is NOT the uv cross-FS story (same FS here). Candidate causes — unverified:
   - slot setup builds `node_modules` with `package-import-method=copy` (a flag in a slot-setup/CI install path), or
   - slot `node_modules` are COPIED wholesale during worktree setup (`setup-tab-worktrees.sh`?) rather than
     `pnpm install`-ed, or
   - per-slot `PNPM_HOME` / `store-dir` env divergence so slots resolve a different (empty) store, or
   - the slots installed at a time the store lacked these wheels and pnpm fell back to copy.

   **The proposed fix only works if the answer is "config/flag/store-resolution."** If slots copy `node_modules`
   wholesale at setup, a store change won't help without also changing the setup path.

2. **Real reclaimable size** — is the 11 GB mostly genuine per-slot copies (the `links=1` evidence suggests yes for the
   slots) or partly already-shared? Needs a proper `du`-with-shared-inodes measurement, not the naive per-dir sum.
3. **Is the reclaim worth the blast radius?** ~6–7 GB (node) vs the ~80 GB the uv fix targeted — much smaller. The
   operator should weigh this explicitly.

## Candidate resolutions (TENTATIVE — pending the unknowns above)

- **A — pnpm shared workspace store (mirror of the uv fix), for `unified-trading-system-ui`:** set
  `store-dir=<workspace>/.pnpm-store` (derived, same-FS, shared) + `package-import-method=hardlink` via a **host-local,
  NOT-committed** `.npmrc` (or env), then `pnpm install` to relink. Fixes the dev-host cross-FS case too
  (`$HOME=/home/hk` ≠ `/active`). **Unproven; depends on Unknown #1.**
- **B — universal `hardlink` (util-linux) sweep over `node_modules`:** package-manager-agnostic, catches npm repos
  without migration; idle-gated in `vm-disk-guard`. **Risk:** pnpm already manages a hardlink+symlink structure under
  `.pnpm`; a blunt FS-level hardlink pass could corrupt pnpm's store-integrity assumptions or break `pnpm install`
  idempotency. Likely must EXCLUDE `.pnpm` and target npm-only dirs — needs review.
- **C — standardize npm repos on pnpm:** the durable answer for `deployment-ui` / `dashboard` / `presentations`, but a
  per-repo migration (lockfile + CI + any flat-`node_modules` assumptions). Separate plan.
- **D — do nothing:** if the reclaim (~6–7 GB) isn't worth the blast radius, document and move on.

## Blast radius

- **Every node repo's install behavior** changes under A/C.
- **CI:** if `store-dir`/`.npmrc` is **committed**, CI runners (own ephemeral FS) may break — a workspace-relative store
  path won't exist there. Any store config MUST be host-local (uncommitted) or CI-aware. (Mirror of the uv "CI owns its
  own cache" rule.)
- **prod:** UI **build artifacts** (`dist/`) ship to prod, not `node_modules` — so prod runtime is unaffected; but the
  CI **build** consumes `node_modules`, so a broken install breaks builds.
- **hardlink sweep (B):** cross-contamination if any postinstall step writes into `node_modules` in place; pnpm store
  integrity if `.pnpm` is touched.

## Questions for the reviewing agent

1. **Root cause of Unknown #1** — why do slot `node_modules` end up as `links=1` copies while root is store-hardlinked?
   (Inspect `setup-tab-worktrees.sh` / any slot pnpm-install path / `package-import-method` resolution.) The whole fix
   hinges on this.
2. **CI safety** — confirm a workspace-derived `store-dir` can be set host-locally without leaking into CI (uncommitted
   `.npmrc` / env only), exactly as the uv cache stayed out of CI.
3. **hardlink-sweep safety** — is a util-linux `hardlink` pass safe over pnpm-managed `node_modules`, or must it exclude
   `.pnpm` and run npm-dirs-only?
4. **Worth it?** Given ~6–7 GB vs the blast radius, is A+B worth doing now, or is D (document + defer) the right call?
5. **Measurement** — confirm the real duplicated footprint with a shared-inode-aware `du`, not the naive per-dir sum.

## Reviewing-agent findings (2026-06-29, claude-opus-4-8, interactive)

All measurements below are from the **dev host** (`/active/unified-trading-system-repos`, `$HOME=/home/hk`). Where a
claim is VM-specific I say so — I could not measure the orchestrator VM from here, and that gap is the one blocking
action.

### A. Premises that CHANGED on re-measurement

- **A1 — On this host the pnpm store is workspace-local + same-FS, so slots ALREADY dedupe.** `pnpm store path` →
  `/active/unified-trading-system-repos/.pnpm-store/v10`, on `/dev/nvme0n1p2` — the **same filesystem** as the repos and
  the `.tabs/<N>` slots. A 2.4 MB real file in `.tabs/23/unified-trading-system-ui/node_modules/.pnpm/firebase@…`
  measures `links=2` — i.e. **hardlinked to the store, not a standalone copy.** So the doc's headline symptom (slot
  `node_modules` = `links=1` standalone copies) is **NOT universally true** — it was measured on the orchestrator VM and
  does not reproduce here. pnpm auto-located its store on the workspace drive, which is exactly what we'd want.
- **A2 — The dev-host cross-FS worry (resolution A's parenthetical) is MOOT.** The doc assumed the dev-host store sits
  at `$HOME=/home/hk` (`/dev/nvme0n1p1`) ≠ the `/active` workspace (`/dev/nvme0n1p2`). It does not — pnpm already placed
  the store under `/active` (p2), same FS as the slots. There is no cross-FS copy-fallback for pnpm on this host. (This
  is the one place the node story **diverges** from the uv story, where the cache genuinely was on the wrong FS.)
- **A3 — Reclaimable size (Q5) is OVERSTATED by the naive per-dir `du`.** Because slot `.pnpm` files are already
  store-hardlinked here, `du -sh slot/node_modules` (1.2 GB) double-counts bytes already shared with the store and other
  slots. A shared-inode-aware measurement (`du` over the union, or `hardlink --dry-run`) will show far less than 6–7 GB
  reclaimable **for the pnpm repos on this host**. The genuine, non-deduped waste is concentrated in the **npm** repos
  (deployment-ui / dashboard / presentations), which have no store-sharing at all — that is the real target.

### B. Unknown #1 — resolved as far as the dev host allows; one VM measurement still required

The slot-`links=1` behaviour the doc saw is **host-specific**, and the cause is NOT a single thing:

- **On the dev host:** no problem to solve for pnpm — store is same-FS and slots hardlink (`links=2`, A1). The only
  dedup gaps here are (i) the **root** UI repo was installed with **npm** (flat `node_modules`, `.package-lock.json`
  present, **no `.pnpm`**) while the slot used **pnpm** — see C1; and (ii) the npm repos never dedupe.
- **On the orchestrator VM (the doc's measurement):** root `.pnpm` = `links=2`, slots = `links=1`, **same FS** — so
  cross-FS is NOT the VM cause. The plausible causes, **none of which I can confirm without measuring on the VM**:
  1. the slots' `pnpm install` resolved a **different store** than root (per-slot `PNPM_HOME`/`store-dir`/`HOME` in the
     tmux-spawn env, or pnpm's per-drive store auto-detection picking a different path than root used);
  2. `package-import-method` resolved to `copy` in the slot context (no reflink + a store on a different device _as the
     slot sees it_);
  3. root and slots were installed at different times against a store that has since moved (the VM ran pnpm **v3** store
     `…/share/pnpm/store/v3` per the doc; this host runs **v10** at the workspace root — the store path is not stable
     across pnpm upgrades).

  **Blocking action (must run ON the VM before any fix):** `pnpm store path`; `df` of that path vs a `.tabs/<N>` slot;
  `pnpm config get package-import-method store-dir`; and the slot tmux-spawn env for `HOME`/`PNPM_HOME`/`PNPM_*`. Until
  that's captured, the VM root cause is a hypothesis and resolution A is not safe to dispatch — exactly the gate the doc
  itself set.

### C. Findings the doc MISSED

- **C1 — codex SSOT contradicts the gitignore "shared install" comment, and the symlink mechanism does not exist.** The
  gitignore template (`scripts/propagation/templates/gitignore-node.txt:12`) and `deployment-ui/.gitignore:77` both say
  "per-slot worktrees **symlink** `node_modules` to a **shared install**." But the codex SSOT
  `codex/05-infrastructure/per-tab-worktrees.md:569-579` says the opposite: slot clones are **code-only**, each repo's
  `node_modules` is built **per-slot** via `npm install` on first frontend op, lives **inside the slot clone**, and is
  "never copied across slots" — no shared install, no symlink. A grep for `ln -s … node_modules` / symlink-creation
  logic finds **only the gitignore comments**, no implementation. So: **there is no symlink-to-shared mechanism** — the
  gitignore comments are stale/aspirational and contradict the SSOT. Resolution A (shared store) is consistent with the
  codex on-demand model (the store is shared, the per-slot `node_modules` is still real) — but **the gitignore comments
  must be corrected** so nobody builds toward a symlink design the codex rejects. The doc should not model "shared
  install" as if it exists.
- **C2 — `unified-trading-system-ui` commits BOTH lockfiles** (`package-lock.json` **and** `pnpm-lock.yaml`). That makes
  the package manager ambiguous and is the most likely real cause of the root=npm / slot=pnpm split I measured. Whatever
  the dedup decision, **the repo must pick ONE package manager and delete the other lockfile** — otherwise installs are
  non-deterministic (different tools, different `node_modules` shapes, different CI behaviour) regardless of any store
  config. This is arguably a higher-priority correctness fix than the disk dedup.

### D. Verdict on the candidate resolutions

- **A (pnpm shared workspace store + `package-import-method=hardlink`, host-local `.npmrc`/env) — ENDORSE, with
  corrections.** It's the correct node-equivalent of the uv fix (pnpm store ≈ uv cache; import-method ≈ link-mode). But:
  make `store-dir` **explicit + workspace-derived** (don't rely on pnpm's auto-drive-detection, which already varies —
  v3 on the VM, v10 here); ensure **slots actually install via pnpm** (C2); and **measure the VM cause first** (B). On
  the dev host this is largely already true (A1), so the win is mostly on the VM + making it deterministic.
- **B (util-linux `hardlink` sweep over `node_modules`) — REJECT for node.** Worse risk than the doc states. (i) It
  isn't enough to "exclude `.pnpm`": pnpm's store is a content-addressed integrity model — a blunt FS hardlink pass that
  merges store files or `.pnpm` virtual-store files can break `pnpm install` idempotency and store verification. (ii)
  For npm repos, `node_modules` is **mutable** far more than a Python venv — `.bin` shims, postinstall scripts that
  patch files in place, native rebuilds — so hardlinking identical files **across different projects** means an in-place
  write in one corrupts the other (the same mutation-semantics risk as the uv hardlink case, but materially more likely
  to fire in node). For a ~6 GB payoff that's already partly realized by pnpm, the blast radius isn't worth it. Use the
  package-manager-native store (A/C), not a filesystem sweep.
- **C (standardize npm repos on pnpm) — ENDORSE as the durable answer, its own plan.** This is what actually fixes the
  npm repos (the real non-deduped waste, A3) and resolves C2. It's a per-repo migration (replace `package-lock.json`
  with `pnpm-lock.yaml`, switch CI `npm ci` → `pnpm install --frozen-lockfile`, check any flat-`node_modules`
  assumptions). Real CI work — correctly scoped to a separate plan, but it's the highest-leverage durable fix, not an
  afterthought.
- **D (do nothing) — partially correct for the dev host pnpm repos** (already deduped), wrong for the npm repos.

### E. Regressions — local vs CI vs prod

- **prod — unaffected.** Only `dist/` build artifacts ship; `node_modules` never reaches prod runtime. ✓ (doc correct)
- **CI — the real surface.** (i) A **committed** `store-dir`/`.npmrc` with a workspace-absolute path breaks on CI's
  ephemeral FS — keep store config **host-local/uncommitted or relative**, mirroring the uv "CI owns its own cache"
  rule. (ii) Resolution C **does** change CI per repo (lockfile + install command) — not zero-cost; stage per repo with
  its own gate-green proof. (iii) Resolution B could leave `node_modules` in a state that fails a clean CI
  `pnpm install --frozen-lockfile` — another reason to reject it.
- **local — resolution B mutation risk (above).** A/C are low-risk.

### F. Answers to the doc's questions

- **Q1 (root cause of Unknown #1):** host-specific; on the dev host pnpm already dedupes (B); the VM cause needs the one
  measurement in B before it can be called. Not "config vs wholesale-copy" yet — could be store-resolution/env. Don't
  design the fix until measured.
- **Q2 (CI safety of a host-local store):** yes — a workspace-derived `store-dir` set via an **uncommitted**
  `.npmrc`/env stays out of CI exactly like the uv cache; a **committed** absolute path does not. Keep it host-local.
- **Q3 (hardlink-sweep safety):** no — reject for node (D/B). Native pnpm store is the safe dedup path.
- **Q4 (worth it?):** for the **pnpm** repos on the dev host, mostly already realized (A1/A3) → low marginal value; for
  the **npm** repos, yes but via C (migrate to pnpm), not B. Net: do A-done-right + the VM measurement now (cheap,
  safe), schedule C as its own plan, skip B.
- **Q5 (measurement):** confirmed — naive per-dir `du` overstates; slot `.pnpm` is already `links=2` here (A1/A3). Use a
  shared-inode-aware measurement on the VM as part of B.

### G. Recommended next steps (ordered)

1. **Fix C2 now** (pick one package manager for `unified-trading-system-ui`, delete the other lockfile) — correctness,
   independent of disk.
2. **Run the VM measurement (B)** — the one gate that unblocks resolution A.
3. **Correct the gitignore "shared install" comments (C1)** to match the codex on-demand model.
4. **Resolution A done right** (explicit workspace-derived `store-dir`, host-local `.npmrc`, ensure slots use pnpm) once
   B confirms the VM cause.
5. **Spin C (npm→pnpm migration) into its own plan** — the durable fix for the npm repos.
6. **Do NOT do B** (FS hardlink sweep).
