# Node `node_modules` dedup — uv-equivalent for node repos?

> **⚠️ DIAGNOSED, NOT PROVEN — REVIEW-GATED. Do NOT implement from this doc yet.** Unlike the uv fix
> (`slot_venv_duplication_disk_pressure_2026_06_29.md`), which was proven end-to-end (clean-room + real-slot inode
> tests) BEFORE shipping, this finding is from symptoms only. The proposed resolution is a **hypothesis** with an
> unresolved root cause and a real blast radius (every node repo's install + possibly CI). It is written specifically so
> a second agent can cross-check it before any change. `assigned_vm: NA`.
>
> **Author honesty note:** during diagnosis I made a measurement error worth flagging — I first sampled a TOP-LEVEL
> `node_modules/<pkg>` entry (got `links=1`) and wrongly concluded "pnpm dedup is broken." The correct target is the
> file UNDER `node_modules/.pnpm/<pkg>@<ver>/...` (pnpm's real store-hardlink target). Re-measuring there changed the
> conclusion. Any reviewer must measure the `.pnpm` path, not the top-level symlink.

## Question being answered

The uv fix deduped Python venvs fleet-wide. Is there an equivalent for the **node/TS repos**
(`unified-trading-system-ui`, `deployment-ui`, `agent-orchestrator/dashboard`, `unified-trading-pm/presentations`),
whose `node_modules` are replicated per slot? And — given the blast radius — is the fix actually safe and worth it?

## What's CONFIRMED (measured)

- **Package managers:** `unified-trading-system-ui` → **pnpm**; `deployment-ui`, `agent-orchestrator/dashboard`,
  `unified-trading-pm/presentations` → **npm** (`package-lock.json`).
- **Total `node_modules` footprint:** **11 GB** (root + slots). Bulk = `unified-trading-system-ui` (~2.3 GB root +
  ~1.1–1.3 GB × ~6 slots ≈ 9 GB). `deployment-ui` ~333 MB × N.
- **pnpm store:** `/home/ubuntu/.local/share/pnpm/store/v3`, **1.2 GB**, on `/dev/root` (same FS as the workspace HERE).
  `package-import-method` = **undefined** (pnpm default `auto`), `store-dir` = **undefined** (default `$HOME` location).
  No committed `.npmrc` in the UI repo.
- **pnpm IS hardlinking to its store — within a repo.** The real file
  `node_modules/.pnpm/lightningcss-linux-x64-musl@1.32.0/.../lightningcss.linux-x64-musl.node` in the ROOT repo is
  `inode=6919311 links=2` (store + node_modules). So pnpm dedup is NOT globally "off" the way uv was.
- **But slots hold STANDALONE copies, not store-hardlinks.** The same `.pnpm` file across slots:

  ```
  root   inode=6919311  links=2   ← hardlinked to store
  slot4  inode=9512795  links=1   ← standalone copy (no store link, no cross-slot share)
  slot5  inode=11797903 links=1   ← standalone copy
  slot6  inode=8240007  links=1   ← standalone copy
  ```

  Different inodes + `links=1` = each slot's `node_modules` is its own physical copy. So there IS real cross-slot
  duplication for the pnpm repo (~6–7 GB plausible upper bound if collapsed to one shared store).

- **npm has no cross-project dedup at all.** npm's cache (`~/.npm/_cacache`) stores download _tarballs_, not unpacked
  packages — every `npm install` re-extracts full copies into each project's `node_modules`. (`vm-disk-guard` wipes
  `_cacache`, which only affects re-download time, not the per-project duplication.)
- **Tooling present:** `pnpm` (`/usr/bin/pnpm`) and `hardlink` (util-linux, `/usr/bin/hardlink`) are installed.

## What's UNKNOWN (the crux — a reviewer must resolve before any fix)

1. **Why do slot installs COPY (`links=1`) while the root install HARDLINKS (`links=2`), on the same filesystem with the
   same `$HOME` store available?** This is NOT the uv cross-FS story (same FS here). Candidate causes — unverified:
   - slot setup builds `node_modules` with `package-import-method=copy` (a flag in a slot-setup/CI install path), or
   - slot `node_modules` are COPIED wholesale during worktree setup (`setup-tab-worktrees.sh`?) rather than
     `pnpm install`-ed, or
   - per-slot `PNPM_HOME` / `store-dir` env divergence so slots resolve a different (empty) store, or
   - the slots installed at a time the store lacked these wheels and pnpm fell back to copy.

   **The proposed fix only works if the answer is "config/flag/store-resolution."** If slots copy `node_modules`
   wholesale at setup, a store change won't help without also changing the setup path.

2. **Real reclaimable size** — is the 11 GB mostly genuine per-slot copies (the `links=1` evidence suggests yes for the
   slots) or partly already-shared? Needs a proper `du`-with-shared-inodes measurement, not the naive per-dir sum.
3. **Is the reclaim worth the blast radius?** ~6–7 GB (node) vs the ~80 GB the uv fix targeted — much smaller. The
   operator should weigh this explicitly.

## Candidate resolutions (TENTATIVE — pending the unknowns above)

- **A — pnpm shared workspace store (mirror of the uv fix), for `unified-trading-system-ui`:** set
  `store-dir=<workspace>/.pnpm-store` (derived, same-FS, shared) + `package-import-method=hardlink` via a **host-local,
  NOT-committed** `.npmrc` (or env), then `pnpm install` to relink. Fixes the dev-host cross-FS case too
  (`$HOME=/home/hk` ≠ `/active`). **Unproven; depends on Unknown #1.**
- **B — universal `hardlink` (util-linux) sweep over `node_modules`:** package-manager-agnostic, catches npm repos
  without migration; idle-gated in `vm-disk-guard`. **Risk:** pnpm already manages a hardlink+symlink structure under
  `.pnpm`; a blunt FS-level hardlink pass could corrupt pnpm's store-integrity assumptions or break `pnpm install`
  idempotency. Likely must EXCLUDE `.pnpm` and target npm-only dirs — needs review.
- **C — standardize npm repos on pnpm:** the durable answer for `deployment-ui` / `dashboard` / `presentations`, but a
  per-repo migration (lockfile + CI + any flat-`node_modules` assumptions). Separate plan.
- **D — do nothing:** if the reclaim (~6–7 GB) isn't worth the blast radius, document and move on.

## Blast radius

- **Every node repo's install behavior** changes under A/C.
- **CI:** if `store-dir`/`.npmrc` is **committed**, CI runners (own ephemeral FS) may break — a workspace-relative store
  path won't exist there. Any store config MUST be host-local (uncommitted) or CI-aware. (Mirror of the uv "CI owns its
  own cache" rule.)
- **prod:** UI **build artifacts** (`dist/`) ship to prod, not `node_modules` — so prod runtime is unaffected; but the
  CI **build** consumes `node_modules`, so a broken install breaks builds.
- **hardlink sweep (B):** cross-contamination if any postinstall step writes into `node_modules` in place; pnpm store
  integrity if `.pnpm` is touched.

## Questions for the reviewing agent

1. **Root cause of Unknown #1** — why do slot `node_modules` end up as `links=1` copies while root is store-hardlinked?
   (Inspect `setup-tab-worktrees.sh` / any slot pnpm-install path / `package-import-method` resolution.) The whole fix
   hinges on this.
2. **CI safety** — confirm a workspace-derived `store-dir` can be set host-locally without leaking into CI (uncommitted
   `.npmrc` / env only), exactly as the uv cache stayed out of CI.
3. **hardlink-sweep safety** — is a util-linux `hardlink` pass safe over pnpm-managed `node_modules`, or must it exclude
   `.pnpm` and run npm-dirs-only?
4. **Worth it?** Given ~6–7 GB vs the blast radius, is A+B worth doing now, or is D (document + defer) the right call?
5. **Measurement** — confirm the real duplicated footprint with a shared-inode-aware `du`, not the naive per-dir sum.
