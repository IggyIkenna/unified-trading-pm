# Codex audit — Alerting area (Phase 1.H)

> **Severity**: P1 — pre-cutover audit per `codex_vs_citadel_infrastructure_audit_2026_05_10.md` Phase 1.H. **Scope**:
> live alert rules · synthetic/test-data filter · severity tiers · on-call routing (Telegram + PagerDuty) · required
> risk events (`CIRCUIT_BREAKER_OPEN` / `KILL_SWITCH_ACTIVATED`) · `AlertCode` enum SSOT · alerting-batch-live · ML
> alert codes · tick-staleness / connectivity-gap taxonomy · the CI-bot Telegram reporting referenced in CLAUDE.md.
> **Owner**: Harsh codex-audit-alerting-tab (slot 8 sub-agent); operator review for dispositions before any Phase 3

## Methodology

Read every Alerting-area codex surface:
`codex/03-observability/{alerting,slos,lifecycle-events,coordination-events}.md`,
`/codex/04-architecture/alerting-batch-live.md`, `/codex/05-infrastructure/live-deployment-monitoring.md`, and the
entire `codex/15-runbooks/alerting/` directory (23 docs — severity glossary, alert-code taxonomy, operator playbook,
PagerDuty escalation policy, threshold tuning, rehearsal procedure, ML alerting rules, + 14 per-AlertCode runbooks). For
each rule / claim / table: cite file:line, classify KEEP / LIFT / CONSOLIDATE / DELETE / ADD, attach a 1-line reason + a
suggested disposition (IMMEDIATE / PRE_CUTOVER / POST_CUTOVER). Cross-checked against `unified-api-contracts`
(`alerting/codes.py` — `AlertCode` / `AlertSeverity` / `AlertChannel` / `KillSwitchScope` StrEnums; `rules.py` —
`LIVE_ALERT_RULES`; `thresholds.py` — `ALERT_THRESHOLDS` + `ThresholdUnit`), `alerting-service/` (router, config, rule
modules, core dispatchers), and `unified-trading-library` (events + kill-switch bus). Several findings come from
grep-then-READ rather than literal-grep-only conclusions (e.g. routing is now UAC-driven via `to_routing_dict()`, not
the inline python block the codex still shows).
