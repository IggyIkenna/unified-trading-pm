# Config Types: Grid vs Runtime

## Two Distinct Config Systems

### 1. Grid Config (Optimization/Iteration)

**Purpose**: Parameter optimization, grid search, backtesting variations

**Services**: strategy-service, execution-service, ml-training-service

**Characteristics**:
- Many configs per run (100s-1000s)
- Generated by scripts (GridConfigGenerator, strategy grid, ML grid)
- Used for optimization (find best params)
- Each config = one backtest/training run
- Stored in domain buckets

**Storage**:
```
gs://execution-store-{category}-{project}/configs/V1/config-{hash}.yaml
gs://strategy-store-{project}/configs/config-{id}.yaml
gs://ml-configs-{project}/configs/config-{id}.yaml
```

**NOT using ConfigStore** - Domain-specific, not runtime config

**Example**:
```yaml
# Grid config for strategy backtest
take_profit: 0.02
stop_loss: 0.01
position_size: 0.1
# ... 50+ params ...
```

---

### 2. Runtime Config (Service Configuration)

**Purpose**: Service runtime parameters, slow-changing, user-editable

**Services**: ALL 14 services

**Characteristics**:
- One config per service (per environment)
- Changes infrequently (days/weeks)
- User-editable via UI or script
- Hot-reloadable in live mode
- Versioned and persisted

**Storage**:
```
gs://config-store-{project}/{service}/
  active.json                    # Pointer to current version
  config-v1708473600.yaml        # Timestamped versions
  config-v1708560000.yaml
```

**MUST use ConfigStore** - UCI provides this

**Example**:
```yaml
# Runtime config for instruments-service
max_workers: 16
log_level: INFO
venues: [binance, coinbase]
enable_defi: true
```

## How Services Should Use Both

### Strategy/Execution/ML Services (Grid + Runtime)

**Grid config** (optimization params):
```python
# Generated by GridConfigGenerator
# Stored in domain bucket
# One per backtest run
grid_config = load_grid_config_from_gcs(config_path)  # Domain-specific
```

**Runtime config** (service params):
```python
# Loaded via ConfigStore
# One per service
# Hot-reloadable
from unified_config_interface import ConfigStore

store = ConfigStore(bucket_name=f"config-store-{project_id}", 
                    service_name="strategy-service",
                    schema_version="1.0")
runtime_config = store.load_config(StrategyServiceConfig)
```

**Both used together**:
```python
# Runtime config: max_workers, log_level, venues
runtime_config = get_runtime_config()

# Grid config: take_profit, stop_loss, position_size
for grid_config_path in grid_configs:
    grid_config = load_grid_config(grid_config_path)
    
    # Run backtest with both
    results = backtest_engine.run(
        runtime=runtime_config,  # Service settings
        params=grid_config       # Strategy params
    )
```

### Other Services (Runtime Only)

**No grid config** - Only runtime config via ConfigStore:

```python
from unified_config_interface import ConfigStore

store = ConfigStore(
    bucket_name=f"config-store-{project_id}",
    service_name="instruments-service",
    schema_version="1.0"
)
config = store.load_config(InstrumentsServiceConfig)
```

## Batch Replay (TimeSeriesConfigStore)

**Use case**: Batch jobs need config that was active on historical dates

**Example**: Reprocessing 2024-01-15 data with config that was active on 2024-01-15

```python
from unified_config_interface import TimeSeriesConfigStore

store = TimeSeriesConfigStore(
    bucket_name=f"config-store-{project_id}",
    service_name="instruments-service",
    schema_version="1.0"
)

# For each date in batch
for date in date_range:
    # Get config effective on this date
    config = store.config_for_date(date)
    
    # Process with historical config
    results = engine.process(data, config)
```

## Hot Reload (ConfigReloader)

**Use case**: Live services need to apply config changes without restart

**Example**: Update max_workers from 16 to 32 without restarting service

```python
from unified_config_interface import ConfigReloader

def on_config_change(new_config: MyServiceConfig):
    logger.info(f"Config hot-reloaded: max_workers={new_config.max_workers}")
    # Apply hot-reloadable changes
    executor.set_max_workers(new_config.max_workers)

reloader = ConfigReloader(config, callback=on_config_change)
reloader.start()  # Subscribes to PubSub
```

**Field metadata**:
```python
class MyServiceConfig(UnifiedCloudConfig):
    max_workers: int = Field(
        16,
        json_schema_extra={"hot_reloadable": True, "requires_restart": False}
    )
    
    api_key: str = Field(
        ...,
        json_schema_extra={"hot_reloadable": False, "requires_restart": True}
    )
```

## Summary

| Config Type | Purpose | Services | UCI Feature | Storage |
|-------------|---------|----------|-------------|---------|
| **Grid** | Optimization, grid search | strategy, execution, ml-training | None (domain-specific) | Domain buckets |
| **Runtime** | Service configuration | ALL 14 services | ConfigStore + TimeSeriesConfigStore + ConfigReloader | config-store bucket |

**Key insight**: Grid configs are NOT runtime configs. They're optimization parameters generated in bulk for backtesting/training.

**Action needed**: Services must adopt ConfigStore/TimeSeriesConfigStore/ConfigReloader for runtime config management.
