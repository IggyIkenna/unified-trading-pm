# Non-canonical path inventory — living register

> **What this doc is.** A durable register of every non-canonical location we currently KNOW about. Before this doc,
> that knowledge existed only in live GCS probes, five issue docs, four closeout plans and two codex docs — so every
> reconciliation run either re-derived it (a whole-corpus GCS walk, **review-blocking** per
> `availability-manifest-and-data-status.md` §9) or lost it at plan archival.
>
> **What this doc is NOT.** It is **not a delete authorization**. A row's disposition is a _standing hypothesis_
> carrying its evidence. The five-part proof in `codex/02-data/gcs-and-manifest-delete-safety-protocol.md` gates every
> actual suggestion, and **prod-bucket deletes are a human-only hard stop**. The canonical grammar this register
> measures against is `cross-asset-canonical-target-ssot.md`; the machine oracle is UAC `canonical_path_violations()`.
> This doc references both and duplicates neither.

## 🔴 DO-NOT-DELETE — read before acting on any row

**`dex_pools/` and `lending_indices/` in `market-data-tick-defi-prd-{pid}` MUST NOT be deleted.** Two live plan docs
(`defi_consolidated_closeout_2026_07_18.md` Track 2 and `canonical_closeout_open_questions_2026_07_18.md` §A6) order a
batch delete of these prefixes as "dead Shape-B duplicates". **That order is stale and would destroy data.** The same

intersection only **66**, with **32 legacy-only high-TVL Raydium pools absent from canonical**). Neither doc was updated
after R5.

Independently corroborated by live probe (2026-07-20, this doc's own verification): under
`raw_tick_data/by_date/day=2026-07-15/`, the two onchain pipeline modes enumerate 20 + 11 `venue=` children and
**venue={ORCA, RAYDIUM, KAMINO, SOLEND} are absent from both** — the canonical twin is **VERIFIED ABSENT**. And
`execution-service` still READS the legacy shape at runtime.

Full disposition + required fold order: `plans/active/issues/defi_dex_pools_delete_order_stale_2026_07_20.md`.

## How to read the `still-written-by` column (this is a correctness gate, not a formality)

`still-written-by: NONE-FOUND` means **a grep over the named repos returned no writer** — it does **NOT** mean the
location is proven unwritten. Writes are frequently runtime-resolved (dynamic prefix construction, config-driven sinks,
one-off VM scripts that live outside the repos, terraform-applied lifecycle rules). Per the workspace's
**grep-then-READ** rule, a NONE-FOUND is the START of an investigation, not its conclusion.

**A reader MUST NOT treat NONE-FOUND as satisfying part (3) of the five-part delete proof.** Part (3) requires a
grep-then-READ proof over the identified candidate consumers, recorded with file:line. Where this register has that
proof, the row says so explicitly; where it only has the grep, it says NONE-FOUND and names what was grepped.

The grep corpus behind every NONE-FOUND below is: `execution-service`, `instruments-service`,
`market-tick-data-service`, `features-service`, `unified-trading-library`, `unified-api-contracts`,
`deployment-service`, `deployment-api` — source trees only (`--glob '!.venv*' --glob '!build'`). **Not grepped**: VM
startup scripts stored in GCS, terraform state, Cloud Run job definitions, notebooks, archived repos.

## Maintenance contract

**Owner**: the data-engineering role — specifically, whoever executes a migration wave or a
`/data-pipeline-reconciliation` campaign. This register has no passive maintainer; it is updated by the person whose
work changes it.

**When it MUST be updated** (each is mandatory, not best-effort):

1. **After each migration wave** — every location the wave created, moved, or emptied gets a row added, moved between
   disposition sections, or retired.
2. **After each `/data-pipeline-reconciliation` run** — any newly discovered non-canonical location found by the Phase-2
   sweep is appended, with its probe date. The skill reads this register; a run that finds something new and does not
   write it back has thrown away the run's most expensive output.
3. **When a disposition changes** — including a downgrade. A row moving from `yes-after-verify` to `no-migrate-first` (a
   twin turned out to be absent or partial) is the single most valuable edit this doc receives, because it is the edit
   that prevents a destructive delete. Record what changed the verdict.
4. **When an audit claim fails verification** — retire it into the audit-trail section above with the disproof, as row
   29 shows. Never delete a row silently.

**Retirement rule — an entry retires ONLY when its disposition is EXECUTED and evidenced.** "Executed" means the
migration/fold/repoint/delete actually ran; "evidenced" means the row cites the run (commit sha, VM/job id, or a dated
post-execution probe showing the new state). **A row does not retire because it was decided, planned, scheduled, or
believed done.** An undated "resolved" is not evidence — row 6 is the standing example: an issue doc marked
`status: resolved` sat above a terraform apply that resurrected ~30 already-deleted buckets.

**Staleness discipline.** Every row carries a probe date or a file:line. A live-probe row older than ~30 days should be
re-probed before it is used to justify a delete; a file:line row must be re-READ (line numbers drift). Rows marked
**UNVERIFIED** were inherited from the 2026-07-20 audit and not independently checked by this doc — they are leads, not
evidence, and **must not satisfy any part of the five-part delete proof** until verified.
