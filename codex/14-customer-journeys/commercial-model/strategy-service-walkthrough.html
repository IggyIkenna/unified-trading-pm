01

What this service is, and what it isn't

? checkowner: strategy_master

This service decides. It consumes features and market state — always the processed kind, delivered through features-service and market-data-processing-service (MDPS), never by reading market-tick-data-service (MTDS) directly — evaluates archetypes each tick, sizes and hedges, and emits typed instructions. It does not connect to venues, work orders, or move funds — those are execution concerns, reached through the contract in §03.

It decidesArchetype evaluation, sizing, hedge ratios, risk vetoes, position monitoring, PnL attribution
It does not executeNo order working, no signing. It emits intent; execution service realises it
One code pathThe same strategy code runs unchanged in batch, paper and live — nothing in it knows which mode it is in
Layout, and why the separation is load-bearing
60Archetypes declared
32Factory-registered
11Instruction types
158Venues in capture
84Venue families
engine/ archetype implementations + the V2 orchestrator that ticks them configs/ one document per strategy instance, plus per-family defaults position/ position monitor, treasury monitor, reconciliation, NAV, margin health risk/ pre-trade risk gates and limit evaluation pnl/ attribution — decision vs execution vs funding transfer_coordinator sweeps, gas reserves, per-client transfer planning close_all/ per-archetype ordered unwind plans

Because a strategy never names an algorithm, execution can be improved — new venues, better order working, different fill models — without touching a single strategy. The reverse also holds: a new archetype inherits every execution capability that already exists.

The gap between 60 declared archetypes and 32 registered is deliberate. An archetype is a named idea; it becomes runnable only when a catalogue builder emits concrete slots for it. Counting declarations as capabilities would overstate what the system can run today.

How to read the status marks

Live means something on a production path calls it and it has been validated with real capital — not that the code exists and passes its tests, and not reachability by itself. Those are three different claims, and only the strictest earns the mark. As of this revision nothing in this document clears that bar: real capital has not moved through any surface described here, so every section that would previously have read live now reads partial.

02

Strategy identity: families, archetypes, slots

partial✓ verifiedowner: W20

Every instruction carries a full identity block. This is what lets a fill in a client report be traced back to the exact strategy build and configuration that produced it.

Archetypes carry a readiness state too — not just venues

Readiness is usually discussed per venue, but an archetype has its own batch / paper / live state, and so does each (archetype, venue) pair. An archetype is only usable on a venue whose data can satisfy the inputs it declares — so "this archetype is ready" and "this venue is ready" are different questions with different answers.

The same rule governs both: derived, never declared. A leg with no real machine check reports unverified rather than passing. Two checks compose into the strategy leg — a position adapter must resolve for that venue in that mode, and at least one archetype's full declared input set must be satisfiable from it. Both, not either.

✓ verified — this now exists as a queryable check, not merely specified. The archetype-code-completeness derivation checks five machine-detectable hooks per archetype per mode — engine registration, parameter schema, target-universe catalogue, allocator rank, and mode-specific dispatch — and falls back to a dated, cited agent-audit record rather than a guess wherever a hook has no clean registry lookup. Measured 2026-08-19 across all 60 archetypes × 3 modes: ~6 ready / ~47 not_ready / ~7 unverified per mode, essentially flat across batch, paper and live. The gap is concentrated, not spread evenly: 18 of 19 VOL_TRADING archetypes and all 4 PORTFOLIO archetypes have no registered v2 engine at all, against 0 of 11 in CARRY_AND_YIELD — so an archetype's family is a strong predictor of whether it is runnable today, well before the mode axis is even reached.

✓ verified — the input side of that check is itself partial today: the registry mapping each archetype to the feature_groups it consumes declares 55 of the 60 StrategyArchetype members (2026-08-18); the rest are explicitly marked undeclared rather than assumed empty, each tracked as a follow-up. An archetype outside that 55 cannot pass the input-satisfiability check above at all yet — not because it fails it, but because the check has nothing to evaluate.

The identity declaration, and how a slot label is built
class StrategyInstanceIdentity: family: StrategyFamily # CARRY_AND_YIELD, VOL_TRADING, PORTFOLIO, … archetype_id: StrategyArchetype # the specific archetype within the family archetype_build_version: str # which build of the archetype produced this strategy_instance_id: str # this running instance slot_version: int = 1 config_hash: str # content hash of the config that produced it config_version: int client_id: str # every instruction is client-scoped share_class: ShareClass env: Literal["prod", "paper", "canary", "dev"] = "prod" holding_wallet: str | None = None wallet_id: str = ""

config_hash is the one to notice. Because it travels on every instruction, the exact configuration in force when a decision was made is recoverable afterwards — a change to a parameter is visible in the instruction stream, not just in a deployment log.

The slot label

CARRY_STAKED_BASIS@lido-uniswapv3-deribit-…-v2-prod │ │ │ │ │ │ archetype │ spot venue │ │ environment staking │ slot version hedge venue

Because the label already encodes the archetype, one archetype can run many simultaneous instances across different venues without ambiguity. That is why configuration, wallet binding and execution policy all key on (client_id, slot_label) — a bare strategy name cannot distinguish two instances of the same archetype on different venues, and that is the normal case rather than the exception.

03

The instruction contract, in full

partial✓ verifiedowner: W18

This is the seam an external strategy would have to satisfy. Every instruction inherits one envelope; the action subclasses add only what that action needs.

What makes one envelope possible across five asset groups

A single instruction contract only works if the thing being traded already has one name everywhere. That is upstream of this section and worth stating, because it is what stops the envelope fragmenting into a per-asset-class dialect: one canonical instrument-ID builder serves every asset group, so a strategy naming an instrument names it the same way whether it is a perpetual, a lending position, a future or an event market.

# CeFi / DeFi / TradFi — the chain rides inside the venue token for DeFi VENUE[-CHAIN]:INSTRUMENT_TYPE:SYMBOL BINANCE-SPOT:SPOT_PAIR:BTCUSDT AAVE_V3-ARBITRUM:LENDING:USDC CME:FUTURE:ES-20260320

The clearest demonstration is event markets, where the same real-world outcome quoted on a sports exchange and on a prediction market resolves to two IDs differing only in the venue token — so comparing them is a group-by rather than an integration:

FOOTBALL:BETFAIR_EX_UK:MATCH_ODDS:EPL:2025-26:ARSENAL-CHELSEA::HOME FOOTBALL:POLYMARKET:MATCH_ODDS:EPL:2025-26:ARSENAL-CHELSEA::HOME

For a strategy author the consequence is concrete: eligible_venues below can list venues from different asset groups against one instrument identity, and the archetype does not need to know which world each venue came from.

The envelope every instruction carries
class StrategyInstructionEnvelope: instruction_id: str emitted_at_utc: datetime # when the strategy decided identity: StrategyInstanceIdentity # §02 — full provenance urgency: Urgency = Urgency.MEDIUM # aggressive vs passive, stated as intent deadline_utc: datetime | None = None execution_policy_ref: str | None = None eligible_venues: list[str] = [] # a set, not a choice venue_constraints: dict[str, VenueConstraints] = {} venue_routing_mode: VenueRoutingMode = SOR_AT_EXECUTION target_venue: str | None = None # only when routing is pinned chain: str | None = None reference_price: Decimal | None = None reference_price_mark_mode: ReferencePriceMarkMode = STATIC_AT_SEND received_at_utc: datetime | None = None # stamped by execution on receipt sent_at_utc: datetime | None = None # stamped when sent to venue attestations: dict[str, str] = {} correlation_id: str | None = None
Three fields worth dwelling on

urgency states intent, never mechanism — it survives a change of venue, of market conditions, and of the execution stack itself. eligible_venues plus a routing mode hands venue choice to execution rather than fixing it at decision time. And the received/sent pair makes latency measurable: decision to receipt is queue time, receipt to send is execution's own processing.

Target-state: a reference price, position and credit — per instrument, not per instruction planned ~ assumed

reference_price only tells execution what the market looked like at instruction time — it says nothing about whether execution's view of strategy's position agrees with strategy's own view. A price gap is a market observation; a position gap is an integrity problem. Price, position, and credit at the same reference point are the whole reference mechanism, not price alone. Because a strategy instance can hold a universe of many instruments at once, that triple has to be a vector — one entry per instrument, not a single flat value on the instruction; an earlier draft of this design put a single per-venue value straight on the envelope, which solves the venue axis (needed for SOR_AT_EXECUTION) but not the instrument axis, and was corrected for that reason. Only reference_price and reference_price_mark_mode are shipped today — everything below is designed, not built.

# proposed addition to StrategyInstructionEnvelope — one entry per instrument in the universe references: list[InstrumentReferenceEntry] = [] class InstrumentReferenceEntry: instrument_id: str reference_price: Decimal reference_position: dict[str, Decimal] # per-venue — SOR_AT_EXECUTION-safe, nested per instrument credit: CreditBand | None = None # strategy-owned, strategy-computed — band (market-making) or hard threshold (arbitrage) position_adjustment_bps_per_unit_risk: Decimal | None = None # symmetric coefficient, against RAW position — generalizes QuoteInstruction.skew_on_inventory class CreditBand: entry_threshold: Decimal | None = None # minimum edge to act abandon_threshold: Decimal | None = None # max adverse move tolerated once committed — optional even when entry_threshold is set

Both fields are governing boundaries strategy sets, not instructions execution must follow mechanically — the same intent-vs-mechanism split execution_policy_ref and AtomicInstruction's own hedge_deadline_ms already draw above. On mismatch, execution would reuse the risk engine's existing four-way consequence rather than a new decision model — but the trigger type itself doesn't exist yet; none of the risk engine's 13 typed trigger conditions covers a position mismatch today. How the vector keys the venue axis, and whether credit varies per entry, are both still open.

~ assumed — design only, not yet implemented; the shape above is illustrative, not final. Full record: execution_delta_proxy_repricer_generalization_2026_08_18.md § "The reference triple is a vector per instrument, not a scalar per instruction."

Targets, not deltas

Trade, lend, borrow, stake, transfer and bridge all express a target state rather than an increment. A transfer or bridge targets a balance at the destination, not an amount to move; re-sending the same instruction is therefore idempotent — it cannot double a position or a movement if a response was lost, which is what makes the contract safe to retry across a service restart.

Reaching this contract over the network — the real endpoint

Strategy-service itself accepts nothing over the network for this contract — it has no counterparty-facing surface at all (checked directly: the shared auth dependency every counterparty router on the platform uses, create_api_auth, has zero call sites anywhere in this repository, 2026-08-20). The envelope above becomes reachable only through execution-service, one HTTP hop downstream.

Method, path, auth

POST /external/instructions on execution-service (execution_service/api/external_instruction_api.py). Gated by the same shared dependency every counterparty router on the platform uses — unified_trading_library.cloud_interface.api_auth.create_api_auth("execution-service") — checked in order: X-Service-Token (S2S), X-API-Key (legacy), or Authorization: Bearer <jwt>. Full header precedence, JWT claim shape and failure modes are not repeated here — see platform-api-reference.html §01.

✓ verified — of the thirteen action types in the envelope above, this endpoint wires exactly two. TRADE executes end-to-end, routed through the same ManualOperationHandler → LiveOrchestrator.execute_instruction() path the internal manual-trade surface uses in production. 04

Configuration surface and the wizard

partial? checkowner: W6

Every archetype declares its parameters in a schema registry rather than in free-form configuration, so the wizard can render a validated form for a new parameter without anyone editing a user interface.

What a parameter declares
class ParamSpec: section: str # reference_price | pnl | analytics | risk wired: bool # does anything actually READ this? key_template: str # where the value lands in the config document enum_source: str # the registry a choice is drawn from
Why wired exists

A configuration surface showing parameters nothing reads is worse than one that omits them: it invites an operator to tune something with no effect, and to believe the result. Making the state explicit turns a silent no-op into a visible one.

enum_source is what stops option lists drifting. A venue choice is drawn from the venue registry rather than a hand-maintained list, so a venue that leaves the system cannot remain selectable.

A separate capability wizard exists too, and the two should not be conflated: it walks readiness gaps across the whole capability graph — venue, instrument and archetype coverage — rather than one archetype's parameter set, which is what this wizard renders.

How configuration reaches a running instance

Configuration is stored per instance and hashed; the hash travels on every instruction (§02). Changing a parameter produces a new config_hash and config_version, so two fills with different behaviour are distinguishable after the fact without consulting a deployment history.

The governing sections separate what a strategy owns from what it merely references. Execution behaviour is deliberately not among them — that belongs to the policy binding in §10.

05

Batch, paper and live — the mode axis

partialnew? checkowner: W1

All three run simultaneously: batch replays on a next-day cadence alongside paper and live running inline. Mode is a property of a strategy instance, never a service-wide setting.

The declared modes, and why testnet sits inside paper
class TradingMode: BATCH = "BATCH" # historical replay — the reference the others prove against PAPER = "PAPER" # the live loop, no client capital at risk LIVE = "LIVE" # real capital, real venues

Testnet is a sub-mode of paper, not a peer of it

Where a venue offers a testnet, paper trades against a real venue-side account and has an independent position to reconcile against. Where it does not — the common case, since many venues have no testnet and those that do often cannot hold realistic balances — paper falls back to simulated matching, using the same matcher batch uses.

Not an implementation detail

That identity is required rather than incidental: it is exactly what makes the determinism proof in §09 meaningful. If paper and batch matched differently, a difference between them would be uninterpretable.

06

Venue coverage: three surfaces, tracked apart

partialnew? checkowner: W5

A venue counts as supported only when three separate things are true. The system now tracks them independently rather than assuming one implies the others — and reports coverage per surface, never as one number.

The capability declaration, and the asymmetry that motivates it
class PositionReadModeAvailability: batch: PositionReadModeStatus = "none" live: PositionReadModeStatus = "none" paper: PositionReadModeStatus = "none" def position_read_mode_availability(venue: str) -> PositionReadModeAvailability

Per venue, per mode. A venue readable in batch but not live is now a visible fact rather than an assumption, which is what a cross-repo check can assert against.

The asymmetry that matters

Being able to act without being able to see is strictly worse than the reverse: the instruction lands, the position changes, and nothing can confirm it or detect drift afterwards. That is why the read side gets its own capability axis rather than being inferred from execution support.

Centralised venues

Broad by construction — the exchange adapter is generic over any supported exchange identifier, so most centralised venues are reachable without a dedicated module. Dedicated adapters exist only where authentication is bespoke.

On-chain venues

Not generic, and where the remaining work sits. Connectors exist ahead of the paths that call them, and the wiring is being closed venue by venue — which is why this section reads partial rather than live.

The measurement, and its date

The gap is measured, not estimated. On 2026-08-15, a caller-graph sweep found 27 of 33 on-chain protocol connector classes had zero production callers — built, tested, and unreachable. That is the number this section's partial status encodes.

Wiring has landed since that sweep — live dispatch for Uniswap, Lido and Jupiter, the instruction router, the recursive-loop orchestrator, Kamino borrow/repay and the Jito connector — so the true figure today is better. It is deliberately not restated here, because it has not been re-measured. A number carried forward without re-measurement is exactly the failure this document exists to avoid; the sweep is now an automated gate, so the next measurement will be a build output rather than a manual count.

Reading positions back

Position reading is the exchange side of reconciliation, and it is read-only by contract — the adapters expose balances, positions and account snapshots, and have no order-placing or signing surface at all.

The read-only contract, and the registry that drives resolution
class BasePositionAdapter(ABC): get_balances() # what we hold get_positions() # open exposure get_account_snapshot() # margin, equity, health get_normalized_positions() venue_name # No create_order. No send_transaction. No withdraw. # The `sign` occurrences are HMAC REQUEST signing for authenticated # reads, not transaction signing.

Registry-driven, so it cannot silently fall behind

def lst_token_address(symbol: str, chain: str = "ETHEREUM") -> str | None def lst_token_addresses_for_venue(venue: str, chain: str = "ETHEREUM") -> dict[str, str]

A venue becomes readable when its token address is added to the shared registry, with no change to the resolver. A venue with no known address is simply not routed — and resolution fails loudly on an unknown venue rather than returning an empty reader.

Why an empty reader would be worse than an error

A reader reporting zero for an unsupported venue would reconcile cleanly against an empty book and hide a real holding. The same rule applies one level down: a venue is never routed to a reader with no tokens to read.

Protocols whose position is genuinely stateful — lending health factors, fixed-maturity instruments, concentrated-liquidity ranges, restaking withdrawal queues — need bespoke readers, because a plain token balance would misrepresent them rather than merely miss them. Those are specified and not yet built.

How a strategy picks: coins, venues, funding

partial? checkowner: W8, W17

A staked-basis or basis strategy is not one trade — it is a choice among many possible (coin × spot venue × hedge venue × staking protocol) combinations. This is how that choice is made and re-made.

The selectable axes, the capability gate, and the liquidity filter

Each axis is enumerated, not hardcoded

# A carry-staked-basis slot is a point in this space: staking_protocol × lst_asset × spot_venue × perp_hedge_venue # spot_venue is a FIRST-CLASS selectable axis — the USDC→native SWAP leg # can route to a centralised spot venue or an on-chain aggregator, # chosen on liquidity rather than fixed at design time.

The catalogue builder emits one slot per viable combination, so adding a venue or an LST expands the opportunity set without new strategy code. Each emitted slot carries its own label (§02), so two combinations of the same archetype are separately configurable, separately funded, and separately killable.

The capability gate comes first

venue_supports_perp_funding(venue) # can this venue hedge at all? perp_hedge_candidate_venues(...) # only those that can

A venue that cannot carry the hedge leg is excluded before any economics are considered. This ordering matters: ranking first and filtering second would let an attractive-looking funding rate produce a slot that cannot actually be hedged.

Then liquidity, then economics

Where the candidate pool is broad — a basis or funding-dispersion book drawing on thirty-plus perp-listed coins across ten venues — the universe is filtered by measured average daily volume to a tractable top-N before economics are evaluated. Liquidity is the binding constraint there, so it is applied as a filter rather than a tie-break.

Where ranking is deliberately NOT used

Staked-basis is not liquidity-ranked. Its universe is a small curated set — a handful of liquid staking tokens, each crossed with the venues that accept them as collateral. That is a capability question, not a liquidity-ranking one, and treating it as the latter would invent choice where none exists.

Funding, and why it is re-evaluated rather than fixed

Funding rates move, and the venue paying best today may not tomorrow. Selection is therefore re-derived on a dated basis rather than pinned at slot creation, and the resolution is a pure function of its inputs — the same inputs produce the same universe, which is what lets a backtest rerun reproduce a live day's choices exactly (§09).

Fees and gas are priced into the decision, not just reconciled afterward

Where a leg has a real gas cost — an on-chain swap or stake inside a basis structure, for instance — that cost is subtracted from the carry the archetype scores candidates on, not merely logged once the trade is placed. When an explicit fee figure is not supplied, the engine estimates it from a real per-tick gas price and the native asset's price rather than assuming zero — the estimate is allowed to be small, never fabricated as a placeholder, and it correctly resolves to zero only when a leg genuinely has no on-chain gas cost to estimate (a CEX-only spot leg, for example).

A registered pattern, not a special case

✓ verified — checked against the staked-basis archetype's fees_apy_bps handling and its _estimate_gas_fees_apy_bps() fallback in strategy-service/strategy_service/engine/strategies/v2/carry_and_yield/staked_basis.py, which sources gas units from UAC's FEES_REGISTRY, 2026-08-18. Other archetypes with an on-chain leg follow the same pattern; this document names one worked example rather than an exhaustive list.

Weighting: a registered set of allocators, not one formula

Once a slot survives selection, how much capital it gets is a separate decision from whether it exists at all — made by a registered set of allocator engines, every one a subclass of one shared base, rather than a single fixed formula. Two families exist side by side: rank-based allocators that run a multi-stage group → filter → weight hierarchy per archetype family, and simpler allocators — fixed, PnL-weighted, Sharpe-weighted, risk-parity, Kelly, minimum-CVaR, regime-aware, manual — for cases that don't need the hierarchy. Adding a new weighting scheme is a new subclass, not a new allocation model bolted on beside the others.

Reconciliation — the engines and the scenarios

partial? checkowner: elysium-disclosure §H.8

Reconciliation is not one comparison. Nine engines cover different surfaces and different moments, and their output can arm a circuit breaker rather than merely log.

The two legs of performance reconciliation
live − batch = (paper − batch) + (live − paper) └── determinism ──┘ └── execution ──┘
paper − batchProves the live loop does what the batch loop does. Same matcher both sides, so any difference is a loop bug. Expected: exactly zero
live − paperWith the loop proven identical, what remains is execution quality alone
Why not compare live against batch directly

It blends the two effects, and a loop bug becomes indistinguishable from poor execution. Isolating the determinism leg first is what gives the second number meaning. Paper over a window must equal a batch rerun trade for trade — not close, equal — because once a tolerance is allowed it can absorb a real bug indefinitely.

The equality's own precondition

That equality assumes paper and the batch rerun select from the same universe on the same day. Dynamic universe selection (§08) is now on by default, and the as-of-date manifest pinning that would guarantee both sides see an identical universe is not yet built — so a paper/batch divergence on a day the universe itself changed is not yet distinguishable from a real loop bug by this check alone.

The engines, by surface
reconciliation_engine positions: internal fill-state vs venue-reported balance_reconciliation_engine balances per venue and wallet fee_reconciliation_engine fees charged vs fees expected pnl_reconciliation_engine attributed PnL vs realised transfer_reconciler transfers instructed vs settled startup_reconciler full reconciliation BEFORE the service accepts data correction_dispatcher bounded automatic correction reconciler_breaker_bridge reconciler output → alert + kill-switch arming

Fee and transfer reconciliation matter more than they sound: a fee schedule that silently changed, or a transfer that left one venue and never arrived at the other, both show up as slow PnL drift that no position check would catch.

Two different territories, not one uniform capability

Position, fee and PnL reconciliation are strategy-owned — checking the strategy's own book against what a venue reports. Balance and transfer reconciliation reach further, across a custodian's own ledger, and sit closer to custody/treasury territory than to strategy decision-making. This section does not mark that boundary by depth of detail; it is worth knowing they are different territories before reading it as one uniform capability.

Four scenarios, and what happens in each

1. Steady state

The internal book is compared continuously against what each venue reports. A discrepancy is surfaced with its size in quantity, in USD value, and as a percentage — so a threshold means the same thing across a thousand-dollar and a million-dollar position.

class ReconciliationSnapshot: internal_quantity: Decimal # what our book says exchange_quantity: Decimal # what the venue says discrepancy: Decimal discrepancy_value: Decimal # USD, so a threshold is comparable across assets discrepancy_pct: Decimal

2. Material discrepancy

Above threshold, a correction can be dispatched automatically — but only through three independent gates: an explicit enable flag, a percentage threshold, and a maximum correctable quantity. All three must pass. The quantity cap is the important one: it stops a bad reading from producing a correspondingly large trade.

3. Service restart

On startup the service fetches all positions directly from venue REST APIs — bypassing local cache — and reconciles before it will accept new data. Critical discrepancies are surfaced first, and the result is returned to the caller so startup can be refused rather than proceeding on a book that may be stale.

Why bypass the cache

A restart is exactly when the cache is least trustworthy — it may predate whatever caused the restart. Reconciling against it would confirm the wrong state and report success.

4. Reconciler failure becomes a circuit breaker

Four state-surface reconcilers — position, balance, custody and on-chain — feed a bridge that raises an alert and arms the kill switch. Reconciliation is therefore not only a reporting function: a book that cannot be trusted stops trading rather than continuing to trade on it.

The execution seam and its config loop

Execution turns an instruction into orders. What matters from the strategy side is what it optimises for, and what governs its behaviour per client.

What it optimises for, and how behaviour is bound per client
Fill the targetWithin the bounds the instruction stated
Close the gapBetween the reference price the strategy supplied and the price achieved
Respect urgencyTrading immediacy against market impact in the direction asked for
Fail loudlyRather than partially, so a half-executed intent is visible instead of silent

The configuration loop

bindings: dict[str, str] # "{client_id}:{slot_label}" -> policy_ref ("policy_id@vN")

Execution behaviour is bound per (client, slot) — the same identity strategies and wallets use. The binding resolves to a policy artefact loaded from object storage and hot-reloaded, so changing how a client's strategy executes needs neither a restart nor a change to strategy code.

The artefact is content-hashed and versioned, so the exact behaviour in force at any moment is identifiable after the fact. Resolution is first-match-wins with a default-deny: an instruction matching no rule does not quietly proceed on a guess.

Deliberately not described here

The rules inside a policy, the thresholds they test, and the algorithms they select. Those belong to execution service, and a strategy is designed never to need them — which is precisely why the strategy side can be read and understood on its own.

Transfers, custody and client isolation

Capital movement is a first-class instruction type, not a side effect. This is the surface that touches an allocator's own custody arrangements, so it is specified in full.

The thirteen transfer types and the three rails
class BusTransferType: # rail it dispatches to CEX_WITHDRAW # CEFI — withdrawal from a centralised venue CEX_DEPOSIT # ON_CHAIN — funding a venue from a wallet SUBACCOUNT_MOVE # CEFI — between subaccounts on one venue DEFI_DEPOSIT # ON_CHAIN DEFI_WITHDRAW # ON_CHAIN BRIDGE # ON_CHAIN — across chains ON_CHAIN # ON_CHAIN — wallet to wallet CUSTODY_TRANSFER # ON_CHAIN — into or out of custody WRAP_UNWRAP # ON_CHAIN SWEEP # ON_CHAIN — dust consolidation REBALANCE # ON_CHAIN — between our own wallets UNITY_WALLET_OP # OTHER IBKR_FUND_MOVE # OTHER

The rail is not cosmetic — it decides which mechanism carries the transfer, and therefore what can fail and how it is confirmed. Note that CEX_WITHDRAW is a CeFi-rail operation while CEX_DEPOSIT is on-chain: the same venue, opposite directions, genuinely different machinery.

Custody: signing surfaces, and where an allocator's arrangement plugs in
class SigningSurface: LOCAL_KEY # development only CLOUD_KMS_ENCRYPTED # key never leaves the KMS boundary COPPER_MPC # Copper multi-party computation custody FIREBLOCKS_MPC # Fireblocks multi-party computation custody MOCK # tests

Custody is a per-wallet property, not a global setting, so a client can hold some wallets under an MPC custodian and others directly without the strategy layer knowing or caring. The signing surface is resolved at the point of signing; the strategy that emitted the instruction never sees it.

What this means for an allocator

If assets sit with a custodian, the integration point is the signing surface and the wallet mapping — not the strategy. Adding a custodian is a wallet-configuration change, and every existing archetype inherits it without modification.

Why Ceffu isn't in this list, and why Fireblocks is

Ceffu has no signing route of its own to declare: its transactions route through Copper (COPPER_MPC above), and its own provider integration is currently a stub. Adding a distinct Ceffu member would invent an enum value the system does not use — the list above is complete as written. Fireblocks, by contrast, does appear (FIREBLOCKS_MPC) but carries an out-of-scope rollout status; the member is retained for future flexibility, not because a Fireblocks integration is wired today.

Treasury versus trading wallets

class ShareClassWalletMapping: # per share class: the treasury wallet, plus trading wallets class TradingWalletConfig: # keyed by (client_id, slot_label) — a wallet belongs to ONE # strategy instance, so exposure is attributable and a slot can be # funded, drained or killed without touching its siblings

The treasury wallet holds the share class's base currency; trading wallets are working capital handed to a specific strategy slot. The split is what makes per-slot funding decisions possible — and what stops a misbehaving strategy from reaching the rest of the book. Funding follows the same binding backward through the rail set above: a CEX_DEPOSIT or DEFI_DEPOSIT targets the specific (client_id, slot_label) wallet that will trade it, not a shared pool divided afterward — so which route a client's capital enters through is a property of which wallet it targets, not a separate routing decision layered on top.

Enforced in code, not by convention

Funds never move between clients. Every transfer is scoped to one client, and an attempt to cross that boundary raises rather than executing. Each client also runs in its own isolated process — so a cross-client transfer is not merely rejected, it has no path to be expressed.

How much goes to each venue

Venue allocation follows the slots that are actually running. Because a trading wallet is bound to one (client, slot), and each slot names its spot and hedge venues (§08), the required balance per venue is a consequence of the enabled slot set rather than a separate allocation model to be kept in sync with it.

Risk: drawdown, leverage, delta, position caps

partial? checkowner: W5, W10

Risk rules sit between a strategy's intent and its execution. A rule that fires can warn, or block the instruction and emit a rejection event — so a blocked instruction is a recorded fact, not a silence.

The limits, and the two-tier warn/breach model
# per client, per slot max_leverage # hard cap max_leverage_warning # fires before the cap, while action is still cheap max_drawdown_pct # hard cap max_drawdown_warning_pct # early tier max_position_usd # notional ceiling per position
Why every limit has a warning tier

A single hard threshold gives you no time: you are either fine or already in breach, and the corrective trade must then happen at the worst moment. The warning tier exists so exposure can be reduced while the market is still orderly — the breach tier is the backstop, not the plan.

Delta neutrality

For strategies that are meant to be market-neutral, residual delta is tracked as a composite across every leg and venue, and evaluated as drift against the share class's base-currency target. Neutrality is therefore a measured property of the whole book rather than an assumption inherited from the strategy's design.

A carry position is only carry while it stays hedged. Drift is what turns it into a directional position nobody chose, which is why the delta composite is monitored continuously rather than checked at entry.

Hedging to minimise added leverage

When exposure must be reduced, the preferred correction is the one that adds least leverage — reducing the existing position where possible rather than opening an offsetting one. Two trades can produce the same net delta while leaving very different gross exposure and margin requirement behind, and the cheaper-looking trade is often the one that increases fragility.

Book-level overlays

Some risk controls apply above the level of any single position. A vol-target overlay is the clearest confirmed example: a directional archetype can size to a target volatility rather than a fixed notional, so exposure contracts automatically when realised volatility rises. A related hysteresis-band pattern — only rebalancing once drift crosses a threshold rather than on every tick — is confirmed at the position level, for peg-tracking hedge ratios.

? check — whether a beta-hedge or rank-buffer control, or the hysteresis-band pattern above, also applies at the whole-book level has not been independently checked for this revision. Stated as design intent, not a verified capability.

Position caps

Notional ceilings apply per position and per slot, so a single archetype cannot consume the book by rule. The stronger claim — that per-slot trading wallets (§11) enforce the same limit by construction, so a slot cannot trade capital it was never given — does not hold today: TradingWalletConfig's get_trading_wallet() lookup has zero non-test call sites in either execution-service or strategy-service. The design intends per-slot wallet funding to bound exposure structurally; that intent is not yet wired to a runtime check, so the rule-based ceiling above is what is actually enforced.

Re-verified, not merely re-read

Kill switches: scoped, and direction-aware
class KillSwitchId: KILL_ALL_LIVE # everything, immediately KILL_PER_ARCHETYPE_CARRY_STAKED_BASIS # one archetype, all clients KILL_PER_ARCHETYPE_ARBITRAGE_PRICE_DISPERSION KILL_PER_ARCHETYPE_ML_DIRECTIONAL_CONTINUOUS KILL_PER_VENUE_BYBIT # one venue, all strategies …

Scope matters: a venue in trouble should not require halting strategies that never touch it, and an archetype behaving badly should not require halting a venue other archetypes depend on. Granular switches mean the response can be proportionate, which makes it far more likely to be used early.

The asymmetry is the point

Protective arming is autonomous; resuming is human-only. An automated system should be able to stop itself and should not be able to restart itself. Every automatic recovery path is scoped to move only in the safe direction.

Emergency flatten is a plan, not a loop

# carry_staked_basis unwind order (close_all/carry_staked_basis.py docstring): 1. cancel resting perp orders on the hedge venue 2. close the perp hedge (reduce-only) 3. repay the Aave borrow 4. unstake / redeem the LST 5. settle on-chain transfers 6. post-close recon check # venue-priority: hedge (CeFi) closed first, then DeFi unwind

Unwinding in the wrong order can leave an account under-collateralised part-way through the sequence — closing a hedge before repaying the borrow it protects is how a controlled exit becomes a liquidation. The plan is therefore per-archetype and venue-scoped rather than a generic loop over positions.

The code enforces two tiers, not six ordered steps ✓ verified

The docstring above states six ordered steps; the actual CarryStakedBasisCloseAll._order_unwind_sequence() only enforces two: every hedge-leg position closes before every DeFi-leg position, in whatever relative order they arrive in current_positions. Repay-before-unstake within the DeFi tier is the stated intent, not a separately-enforced ordering in this function today.

Auto-resolution and escalation

partialnew? checkowner: W4

When a dependency fails, the response is graduated rather than binary. Each failure maps to an action and an escalation target, so most problems resolve without a human and the ones that reach a human are the ones that should.

The action ladder and the escalation ladder
class DependentAction: # least to most severe NONE SELF_RETRY # transient — try again SELF_RESTART # this service is wedged SELF_DRAIN # stop taking new work, finish what is in flight DEPS_HOLD # hold dependents back DEPS_DRAIN # drain dependents too FLEET_HALT # stop the fleet KILL_SWITCH # arm protection (§12) class EscalationTarget: AUTO # resolved without notifying anyone AGENT # an automated operator picks it up AGENT_URGENT HUMAN # wallet keys, credentials, and every manual_unkill resume

The two ladders are independent: a severe action can still be automatic (arming a kill switch), and a mild condition can still need a human (anything touching credentials). Pairing them per failure mode is what stops the system either over-escalating routine faults or quietly self-healing something that warranted attention.

The rule that anchors it

Protective arming is autonomous; manual_unkill resume is human-only. The ladder can always move toward safety on its own, and never away from it.

Draining rather than stopping

SELF_DRAIN and DEPS_DRAIN matter more than they look. Stopping abruptly leaves in-flight orders in an unknown state; draining refuses new work while letting what is already committed complete, so the book is in a known condition when the service does stop — which is exactly what the startup reconciler (§09) then checks against.

14

Orders and the audit record

partialnew? checkowner: W11

Positions, trades, fills, orders and the strategy instructions that caused them are one class of private record: the entry is immutable, and the actions taken on it are auditable.

Append-only records, and why attempts are recorded too

Audit entries are append-only objects with a validated schema. Records are never edited in place and never removed — a withdrawal is a status change plus an audited action, so both the original entry and the fact of its removal survive.

Attempts count, not only outcomes

A cancel that races a fill must be distinguishable from a cancel after confirmation. Both may end in the same final state, but only one is an attempt to intervene while the order was still in flight — and that distinction is precisely what an audit is asked for after the fact.

Marked partial deliberately

The immutable primitive exists and is used by the manual path. Extending it across automated orders, fills and instructions — and adding vocabulary for attempted actions — is specified and open.

15

PnL, ledgers and the high-water mark

partial? checkowner: W13

Performance is attributed across parallel ledgers rather than collapsed into one number, so the source of a difference is identifiable rather than inferred.

Parallel ledgers, flow-adjusted marks, attribution dimensions

The same window can be viewed as it actually filled, as it would have filled at the reference price, and as the batch rerun produced it — which turns "execution cost us X" into a measured quantity rather than an estimate.

The high-water mark is never raw equity

A mark computed on raw equity moves when a client deposits or withdraws, which has nothing to do with performance. The mark is computed on a flow-adjusted basis instead, so subscriptions and redemptions neither create nor erase a fee position.

Attribution dimensions

PnL decomposes by venue, account, client, instrument and strategy slot — the same identity from §02, which is what lets a number in a client report be traced back to the instructions that produced it.

16

Backtest fidelity

partial? checkowner: W3

A backtest is only as honest as its fill assumptions. Fidelity is explicit: the system knows what data quality a given instrument and period had, and never claims a better fill model than the data supports.

The tiers, the clamp direction, and the benchmark mode
class ExecutionFidelityTier: OHLC_BAR = 1 # open/high/low/close only CANDLE_BOOK_COLS = 2 # bars with book-derived columns L2_TICK = 3 # full depth and trades def clamp_tier(requested, available) # clamps DOWN only, never up
The clamp direction is the safeguard

A request for a richer model than the data supports is degraded to what is defensible, never upgraded. An optimistic fill model flatters a backtest in exactly the way that is hardest to notice.

Graceful fallback

Where finer data exists it is used; where it does not, the model steps down a tier rather than refusing to run. An instrument with no tick history is still testable, with its fills marked as the coarser estimate they are.

The benchmark comparison

A separate mode replaces execution entirely, filling every instruction at the strategy's own reference price. The difference between that and a realistic fill isolates execution's contribution from the strategy's — the same decomposition as §09, applied inside a single backtest.

Settled since the last revision

Four decisions closed that previously blocked work, and they change what the target looks like rather than just how fast it arrives.

Readiness is derived, never declared. A venue's state is computed from the contract steps, so it cannot drift — and a step with no real check reports unverified, never a pass. Granularity is declared per venue, so execution refuses a matching class the data cannot support instead of matching as though it had tick data. Error semantics are one registry keyed by venue and code, so a venue's failure behaviour is known before production rather than discovered in it. Service configuration is one module per service, schema-backed and hot-reloadable, so "what is this configured to do" never requires reading implementation.

Risk limits ship as our own operating values rather than conservative defaults — the same numbers we run, so behaviour matches the record, with every limit remaining config-overridable. They are our values, not a calibration to someone else's balance sheet.

Signal leasing — a second external surface

partialnew✓ verified owner: signal-leasing launch (2026-09-01)

§03 above is one way an outside party reaches what this service produces: hand strategy-service's decision to execution-service and let it trade on your behalf. This is the other: Odum keeps execution entirely, and a counterparty instead subscribes to the signal itself and self-executes. Not documented anywhere else in this walkthrough as of the previous revision — added here because it is real, built, and reachable, which is exactly the bar the rest of this document holds everything else to.

"Counterparty" is not a client

A signal-leasing Counterparty is a distinct entity from a ClientDefinition — Odum's paying investment-management clients or SaaS subscribers. Counterparties pay a per-slot subscription to receive emitted signals; they have no portfolio allocation, no share-class mapping, and no capital routed through Odum's infrastructure at all. What travels to them is the archetype's directional intent and sizing, not a trade, not custody, not a fill.

✓ verified — checked against unified_api_contracts/internal/domain/signal_broadcast/counterparty.py module docstring and the Counterparty model (id, allowed_slots, hmac_secret_ref, rate_limit_ref), 2026-08-20.

Two transports, one contract: webhook push primary, REST pull as fallback

Emissions are pushed to the counterparty's own webhook endpoint first — HMAC-SHA256-signed, with retry and exponential backoff on 5xx/connection errors, giving up on 4xx except 408/429. The REST-pull surface below exists for reconciliation: a counterparty that missed a push, or wants to replay a window, pulls the same emissions back out of a bounded in-memory ring buffer (256 per counterparty by default), and can acknowledge out of band. Both paths write to the same audit trail, so "did they get it" has one answer regardless of which route delivered it.

Auth is per counterparty, not the platform's shared mechanism

This surface does not use the create_api_auth dependency §03 documents for execution-service. Every request carries Authorization: Bearer <jwt>, an HS256 JWT signed with that counterparty's own secret (resolved from Secret Manager via hmac_secret_ref, never held as a plaintext literal). The router decodes the token against the exact counterparty named in the request and rejects a token that does not match — one secret buys access to one counterparty's own data, never another's.

A liquidation, a stop or a take-profit trigger on this platform is event-triggered, not schedule-polled; nothing in this surface implies otherwise, and no section of this document should be read as claiming a fixed-cadence risk check.

Rate limiting, errors, and the honest launch state

Emission dispatch — not the REST-pull GET itself — is token-bucket limited per (counterparty_id, strategy_id), via a named RateLimitConfig profile resolved from Counterparty.rate_limit_ref: default (10 req/s, burst 10), minimal (5 req/s, burst 5), burst (25 req/s, burst 50). A counterparty at its cap is not dropped silently — the emitter records rate_limited and the event is visible in delivery health.
