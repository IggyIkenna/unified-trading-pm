What this repository is, and what it isn't

This service decides. It consumes features and market state, evaluates archetypes on each tick, sizes and hedges, and emits typed instructions. It does not connect to venues, work orders into the market, or move funds itself; those are execution-service concerns, reached through the contracts in §03.

The governing rule is the tier model: imports only ever point downward, and no service imports another service. This repository depends on the shared library and the contracts package, and on nothing else in the estate. What is deliberately not here

Execution algorithms and order routing, venue adapters and connectivity, custody signing, market-data capture, and feature computation all live in other services. Where this repository needs one of them it holds an interface, not an implementation. Those seams are the subject of §03 and §11.

Nothing in this service is addressed by a bare strategy name. A running decision-maker is identified by a four-part coordinate, family, archetype, instance and slot, and that coordinate is stamped onto every instruction it emits. The strategy → execution contract

This likely is most important part because it is the boundary Strategy would integrate against. Every strategy in every family emits one of the 16 instruction types, all sharing a common envelope. The envelope is where the interesting design sits.

The envelope, every instruction carries this

class StrategyInstructionEnvelope(BaseModel): instruction_id: str emitted_at_utc: datetime identity: StrategyInstanceIdentity urgency: Urgency = Urgency.MEDIUM deadline_utc: datetime | None = None execution_policy_ref: str | None = None # names a policy; does not contain it attestations: dict[str, str] = {} # compliance trail correlation_id: str | None = None eligible_venues: list[str] = [] # where it MAY go venue_constraints: dict[str, VenueConstraints] = {} venue_routing_mode: VenueRoutingMode = VenueRoutingMode.SOR_AT_EXECUTION target_venue: str | None = None chain: str | None = None reference_price: Decimal | None = None # strategy-set benchmark price execution marks fills against reference_price_mark_mode: ReferencePriceMarkMode = ReferencePriceMarkMode.STATIC_AT_SEND received_at_utc: datetime | None = None # stamped by execution-service on receipt sent_at_utc: datetime | None = None # stamped by execution-service when the order reaches the venue class VenueConstraints(BaseModel): max_notional_usd: Decimal | None = None min_liquidity_usd: Decimal | None = None fee_tier: str | None = None max_slippage_bps: int | None = None

A cluster of fields carries most of the permission-and-provenance meaning. eligible_venues plus venue_constraints say where an instruction is permitted to be worked and under what limits; venue_routing_mode defaults to SOR_AT_EXECUTION, meaning the venue choice is made at execution time rather than by the strategy; and execution_policy_ref names an execution policy without containing it. The strategy therefore expresses intent and permission, and never expresses method. That separation is enforced by the type, not by convention.

reference_price carries a different kind of meaning, and it is shipped on the envelope today; it lives there rather than on any one instruction type so any instruction can carry a benchmark price, and reference_price_mark_mode says whether execution marks fills against it as sent, or re-derives it as the underlying moves. But price alone is one leg of a three-leg design, not the whole reference mechanism: strategy is meant to state its per-instrument position and credit at the same reference point too, so execution can approximate how to adjust on a tick basis as new position/price information arrives without re-consulting slow-path strategy; that triple, not price on its own, is the entire reason the fast-path/slow-path split works. Strategy sets the governing boundary; execution decides the mechanics within it. Only the price leg and the mark-mode flag exist in code today; the position and credit legs are designed, not built (see the callout below). Execution additionally stamps received_at_utc and sent_at_utc on every instruction it touches, so the strategy-side-to-order-placed latency is a field, not a log-mining exercise.

Target-state: a reference price, position and credit, per instrument, not per instruction

A price can legitimately differ from the reference; the underlying moved. A position mismatch is a different kind of problem: it means execution's view of what strategy holds disagrees with strategy's own view, which is an integrity check, not a market observation. Price, position and credit at the same reference point are the whole mechanism, not price alone, and because a strategy instance can hold a universe of many instruments at once, that triple has to be a vector, one entry per instrument, not a single flat value on the instruction. An earlier draft of this design put a single per-venue reference_position straight on the envelope; that solves the venue axis (which venue, when venue_routing_mode is SOR_AT_EXECUTION and the venue isn't picked until execution time) but not the instrument axis, and was corrected for exactly that reason.

class InstrumentReferenceEntry: instrument_id: str reference_price: Decimal reference_position: dict[str, Decimal] # per-venue, same shape as before, now nested per instrument credit: CreditBand | None = None # band (market-making) or hard threshold (arbitrage) position_adjustment_bps_per_unit_risk: Decimal | None = None # symmetric coefficient, against RAW position class CreditBand: entry_threshold: Decimal | None = None # minimum edge to act abandon_threshold: Decimal | None = None # max adverse move tolerated once committed, optional even when entry_threshold is set # proposed addition to StrategyInstructionEnvelope, one entry per instrument in the universe references: list[InstrumentReferenceEntry] = []

credit is strategy-owned and strategy-computed, the same intent-vs-mechanism split execution_policy_ref already draws elsewhere; position_adjustment_bps_per_unit_risk generalizes QuoteInstruction.skew_on_inventory (§03) off market-making specifically. Both are governing boundaries the strategy sets; which algo runs and how it stays inside them remains execution's call, the same relationship hedge_deadline_ms (§03, AtomicInstruction) already has with the algo layer. On mismatch, execution would reuse the risk engine's existing four-way consequence (BLOCK / SCALE_DOWN / MONITOR / TEST_ONLY) rather than invent a second decision model, but the trigger type itself doesn't exist yet: none of the risk engine's 13 typed trigger conditions covers a position mismatch today, so wiring this needs a new trigger type added to that closed set, not just consumption of an existing one.

Exactly how the vector is keyed is still open, not decided: nesting per-instrument-then-per-venue (as sketched above) assumes one strategy instance never wants two different believed positions for the same instrument across venues within one instruction, true today, not re-confirmed for a multi-instrument vector. Whether credit and the adjustment coefficient vary per entry or apply once across the whole vector is also open. A cross-instrument version of this, how a fill in instrument B should move the acceptable adjustment on instrument A, is real but deliberately out of scope here: it would live as a fast-path approximation module inside execution-service, relevant only where A and B are non-fungible (a cross-chain staked-basis leg, or options across different terms or strikes), and is stubbed rather than built.

This is design only. The shape above is illustrative rather than final, and the questions listed with it are genuinely open rather than resolved and abbreviated.

One scoping note belongs with it: this reference-price, position and credit mechanism, and position_adjustment_bps_per_unit_risk in particular, is the continuous-quote fast-path kernel, not a universal repricing formula across asset groups. A DeFi AMM leg is repriced by exact reserve/tick-math simulation, and a sports or prediction leg by a finite-state posterior lookup; the Jacobian/Hessian Taylor form this design sketches is one of three profile-specific kernels, not the general case.

What the timeframe, the "SCE" id suffix and the health-factor ladder actually mean

The strategy_id above carries a _SCE_1H suffix. Read against this codebase's own hold-policy rule (SCE = SAME_CANDLE_EXIT, and, verbatim, "DeFi strategies are NEVER SCE (gas + confirmation latency); SCE is only for CeFi/TradFi ML strategies with explicit TP/SL"), that suffix is stale: a staked-basis carry position is entered and held, not round-tripped every candle. The field that actually governs behavior, two lines above it, execution_mode: continuous, is correct; this is HOLD_UNTIL_FLIP-style behavior (exit when the carry stops being profitable), not same-candle exit. against the strategy's own held, multi-leg close-all logic below; the id string itself is an unfixed naming leftover, tracked separately and not this document's to fix.

timeframe: 1h sets the candle/feature-bar resolution the engine's tick loop advances on; it is a feature and re-evaluation cadence, not a risk-monitoring one. That distinction matters directly for the health-factor ladder just above it.

Liquidation risk does not wait for the next candle

The ladder above (health_factor_target / _emergency_reduce_at / _emergency_close_at) is read synchronously on every tick via a fail-closed cache (position/core/margin_health_cache.py, a miss or a stale read both block the trade, never "no check, proceed"), but that read is bounded by the strategy's own cadence, and an hourly re-evaluation is far too slow for a health factor that can move meaningfully in seconds. The real liquidation trigger does not run on this strategy's timeframe at all: execution_service/defi_execution/monitors/health_factor_monitor.py's HealthFactorMonitor is a near-block-time loop per chain (Ethereum ~12s via WS eth_subscribe newHeads with poll fallback, Base 2s, Arbitrum ~1s debounced), firing DEFI_HEALTH_FACTOR_CRITICAL (HF < 1.10) and DEFI_LIQUIDATION_IMMINENT (HF < 1.05) independently of any strategy poll. A separate, portfolio-wide LIQUIDATION_CASCADE_RISK circuit breaker fires KILL_ALL at Aave HF ≤ 1.10 across ≥ 2 positions, a cross-position check, differently scoped from this one strategy's own health_factor_emergency_close_at: 1.0 floor, not a duplicate of it. These are three separate mechanisms at three different scopes, not one hourly poll.

HealthFactorMonitor is real, written code, but this pass found zero call sites constructing it anywhere in execution-service outside its own module: whether anything actually runs it in production was not confirmed.

What execution does when it fires: execution_service/algo_library/deleverage_executor.py's DeleverageExecutor is a MarginEvent-driven Pub/Sub subscriber, event-triggered, not scheduled, dispatching an asset-group-aware action on CRITICAL/LIQUIDATION severity: for DeFi, top_up_collateral on CRITICAL, repay_debt ("repay borrow + withdraw collateral") on LIQUIDATION. For a full unwind rather than a step down in leverage, the strategy's close-all script, CarryStakedBasisCloseAll, runs a real, ordered sequence: cancel resting perp orders on the hedge venue, close the perp hedge (reduce-only), repay the Aave borrow, unstake/redeem the LST, settle on-chain transfers, then a post-close recon check. read in full; the actual _order_unwind_sequence() implementation only enforces a coarser two-tier grouping (every hedge-leg position closes before every DeFi-leg position), not the finer six-step total order its own docstring states; repay-before-unstake within the DeFi tier is stated intent, not independently enforced by that function today. the dispatch logic above is real and unit-testable; whether a live subscription actually calls DeleverageExecutor in production execution-service was not traced in this pass.

How a parameter is declared, and how configuration reaches a running instance

Every v2 archetype declares its parameters in a schema registry rather than in free-form configuration, which is what lets the onboarding wizard render a validated form for a new parameter without anyone editing a user interface. engine/strategies/v2/param_schema.py's ParamSpec is the declaration, and PARAM_SCHEMA_REGISTRY is the lookup get_strategy_params() uses to fill defaults:

class ParamSpec: name: str # the key as read from the flat params dict, e.g. entry_bps type: str # int | float | decimal | str | enum | bool default: str | None # None for a required param with no literal default required: bool # True if the engine lists it in REQUIRED_PARAMS, or no-ops without it

The value of declaring required against real engine behaviour rather than against a hand-kept list is that a configuration surface showing parameters nothing reads is worse than one that omits them: it invites an operator to tune something with no effect and to believe the result. Enumerated choices are drawn from the owning registry rather than a maintained option list, so a venue that leaves the system cannot remain selectable.

Configuration is stored per instance and hashed, and the hash travels on every instruction (§02). Changing a parameter produces a new config_hash and config_version, so two fills with different behaviour are distinguishable after the fact without consulting a deployment history. Which loader actually resolves an instance's configuration at boot, and which one the YAML above is written against, is traced in §06, 6.1. Execution behaviour is deliberately not part of this surface; it binds separately, per client and slot (§12).

Two orthogonal axes, not one flat list

# unified_api_contracts.internal.modes class RuntimeMode(StrEnum): LIVE = "live" BATCH = "batch" # the process-level axis class OperationalMode(StrEnum): LIVE = "live" MANUAL = "manual" BACKTEST = "backtest" PAPER = "paper" # the per-archetype execution semantics, no TESTNET member class ExecutionTarget(StrEnum): MAINNET TESTNET FORK SIMULATION # WHERE the mode points, an independent axis # unified_api_contracts.internal.reconciliation class TradingMode(StrEnum): PAPER = "PAPER" BATCH = "BATCH" LIVE = "LIVE" # which of the three produced a run, stamped on reconciliation output

The service's own CLI takes --mode batch|live|paper. The important structural point is that OperationalMode has no TESTNET member and never will: testnet is a value of ExecutionTarget, which is a separate axis. The deprecated collapsed enum makes this explicit in code, because its decompose() method maps TestingStage.LIVE_TESTNET onto the triple (OperationalMode.PAPER, ExecutionTarget.TESTNET, ExecutionTrigger.AUTOMATED). Testnet is paper pointed at a testnet.

What paper actually resolves to, per venue

position/position_interface/base.py's BasePositionAdapter carries the mode axis on every adapter instance, and its own docstring is the clearest statement of the rule: 

LIVE mainnet or production venue endpoints; testnet must be False

PAPER + testnet=True a real venue-side paper account (Binance testnet, IBKR paper TWS) or, for DeFi, a real
public testnet chain, reachable by real API and RPC calls

PAPER + testnet=False the shared simulated matcher, THE SAME matcher batch uses; no per-venue adapter, resolved
to LedgerPositionAdapter by the factory

BATCH the as-if-filled PositionLedger, the reference leg paper is proven against; not a venue read at all

Where a venue offers a testnet, paper trades against a real venue-side account and therefore has an independent position to reconcile against. Where it does not, which is the common case, paper falls back to the same matcher batch uses. That identity is required rather than incidental: it is exactly what makes the determinism proof in §08 meaningful, because if paper and batch matched differently then a difference between them would be uninterpretable.

A third flag that looks like testnet and is not

DeFi's fork_mode, which selects an anvil or tenderly local-fork RPC, is a separate and independent flag. It is an RPC-resolution mechanism valid under any mode, including a local-fork dry run under LIVE, and is never itself evidence of testnet=True. The adapter base class rejects testnet=True outside mode=PAPER, so the two cannot be conflated by accident.

The per-tick mode gate

engine/strategies/v2/mode_store.py's ArchetypeModeStore is a process-global singleton holding a per-archetype OperationalMode override, and any archetype it has never been told about reads back as MANUAL. V2EngineOrchestrator._tick_one_engine() consults it on every tick and returns an empty instruction list when the mode is MANUAL. The default is therefore silence, and an archetype has to be deliberately promoted before it can emit anything. The HTTP surface for that promotion is POST /api/archetypes/{id}/operational-mode, which enforces the allowed transition set and answers 409 on a disallowed hop such as manual straight to live (§13).

How a strategy picks: coins, venues and funding

A basis or staked-basis strategy is not one trade. It is a choice among many possible combinations of coin, spot venue, hedge venue and staking protocol. Each axis is enumerated from a registry rather than written into the archetype, and the order in which the axes are cut down matters as much as the criteria themselves.

Capability first, economics secondA venue that cannot carry the hedge leg is removed before any rate is looked at
Gas and fees are priced inEstimated from a real per-day gas price and the UAC fees registry, never assumed to be zero
Weighting is a registered setAllocators are subclasses behind one lookup, not a single formula with switches
The selectable axes, the capability gate, the liquidity filter and the allocator registry

Each axis is enumerated, not hardcoded

# a carry-staked-basis slot is a point in this space staking_protocol × lst_asset × spot_venue × perp_hedge_venue # spot_venue is a first-class selectable axis: the USDC to native swap leg # can route to a centralised spot venue or an on-chain aggregator, chosen # on liquidity rather than fixed at design time

The catalogue that emits those points is engine/strategies/v2/target_universe/catalog.py, a facade composing catalog_carry.py, catalog_staked_basis.py, catalog_directional.py, catalog_trading.py, catalog_yield_defi.py and catalog_expansion.py. It emits one slot per viable combination, so adding a venue or an LST expands the opportunity set without new strategy code. Each emitted slot carries its own label (§02), which is what makes two combinations of the same archetype separately configurable, separately funded and separately killable.

The capability gate comes first

# engine/strategies/v2/target_universe/venue_capabilities.py def venue_supports_perp_funding(venue) -> bool # can this venue hedge at all? def perp_hedge_candidate_venues(...) -> ... # only those that can

A venue that cannot carry the hedge leg is excluded before any economics are considered. The ordering is the substance of the rule: ranking first and filtering second would let an attractive-looking funding rate produce a slot that cannot actually be hedged.

Then liquidity, then economics

Where the candidate pool is broad, a funding-dispersion book drawing on dozens of perp-listed coins across ten venues for instance, the universe is cut to a tractable top set by measured average daily volume before economics are evaluated. That filtering lives in the allocator rather than in the catalogue; discrete_structure_allocator.py is where it happens. Liquidity is the binding constraint in that setting, so it is applied as a filter rather than as a tie-break.

Where ranking is deliberately not used

Staked basis is not liquidity-ranked. Its universe is a small curated set, a handful of liquid staking tokens each crossed with the venues that accept them as collateral, and catalog_carry.py says so in its own comments. That is a capability question rather than a liquidity-ranking one, and treating it as the latter would invent choice where none exists.

Funding is read fresh, not pinned at slot creation

Funding rates move, and the venue paying best today may not tomorrow, so selection is re-derived rather than pinned when the slot is created. Concretely this is not a scheduled re-evaluation component; there is no separate funding-refresh module. Funding enters the decision as a feature input read on every tick, for example funding_rank_pct and funding_rate_annualised_bps in carry_and_yield/funding_dispersion.py, and the resolution is a pure function of those inputs. That purity is what lets a batch rerun reproduce a live day's choices exactly (§16).

Fees and gas are priced into the decision, not reconciled afterwards

Where a leg has a real gas cost, an on-chain swap or stake inside a basis structure for instance, that cost is subtracted from the carry the archetype scores candidates on rather than merely logged once the trade is placed. cli/handlers/paper_run_handler.py's _gas_price_gwei_for_day() reads the real per-day mean base fee from the captured gas-fee corpus, the same reader post-trade P&L gas accounting uses, and carry_and_yield/staked_basis.py's _estimate_gas_fees_apy_bps() converts it into a basis-point drag using gas units from the UAC FEES_REGISTRY. Where no explicit fee figure is supplied the engine estimates rather than assuming zero; the estimate is allowed to be small, and it resolves to zero only when a leg genuinely has no on-chain gas cost, a centralised spot leg for example.

Weighting: a registered set of allocators, not one formula

Once a slot survives selection, how much capital it gets is a separate decision from whether it exists at all. portfolio_allocator/archetypes.py's get_allocator_archetype_engine(archetype) is the single lookup, and every allocator behind it is a subclass of one shared base. Two families sit side by side: the rank allocators in archetypes_rank.py, which run a multi-stage group, filter and weight hierarchy per archetype family (CarryBasisPerpRankAllocator, CarryFundingDispersionRankAllocator, CarryStakedBasisRankAllocator, YieldRotationLendingRankAllocator, ArbitragePriceDispersionRankAllocator and their siblings, all on BaseRankAllocator), and the simpler allocators in archetypes_simple.py, which cover fixed, P&L-weighted, Sharpe-weighted, risk-parity, Kelly, minimum-CVaR, regime-aware and manual weighting for cases that do not need the hierarchy. Adding a weighting scheme is a new subclass rather than another branch inside an existing formula. An allocation that fails the service's own gate raises AllocationGateDeniedError instead of silently returning a zero weight.

Reconciliation: the engines and the scenarios

Reconciliation here is not one comparison. Separate engines cover separate surfaces and separate moments, and their output can arm a circuit breaker rather than only write a log line. A book that cannot be trusted stops trading rather than continuing to trade on itself.

Positions are one surface of severalBalances, fees, P&L and transfers each get their own engine and their own thresholds
Discrepancies have a lifecycleTransient, confirmed, then auto-reconciled or escalated; not a single boolean
Reconciler failure is a breaker inputFour state-surface reconcilers feed a bridge that alerts and can arm the kill switch
The two legs of performance reconciliation
live − batch = (paper − batch) + (live − paper) └── determinism ──┘ └── execution ──┘
paper − batchProves the live loop does what the batch loop does. The same matcher on both sides, so any difference is a loop bug. Expected value: exactly zero
live − paperWith the loop proven identical, what remains is execution quality alone

The reason not to compare live against batch directly is that it blends the two effects, and a loop bug then becomes indistinguishable from poor execution. Isolating the determinism leg first is what gives the second number meaning. Paper over a window must equal a batch rerun trade for trade, not approximately, which is why the reconciliation engine bypasses its graded thresholds entirely on the determinism leg (§06, 6.3).

The equality has its own precondition

It assumes paper and the batch rerun select from the same universe on the same day. Dynamic universe selection (§07) is on by default, and the as-of-date manifest pinning that would guarantee both sides see an identical universe is specified rather than built. A paper against batch divergence on a day the universe itself changed is therefore not yet distinguishable, by this check alone, from a real loop bug.

3. Service restart

StartupReconciler.run() is invoked by position/engine/orchestrator.py's StartupOrchestrator before the service reports itself started, and it runs a blocking reconcile_all_positions() using the same engine and the same method as the steady-state cycle. There is deliberately no second rehydration algorithm to drift from the first. Position state is fetched directly from venue REST endpoints rather than from any local cache, because a restart is exactly the moment the cache is least trustworthy: it may predate whatever caused the restart, and reconciling against it would confirm the wrong state and report success.

Per-venue shard isolation applies here too. _run_one_venue_shard_safely() catches connection, timeout, OS, value and runtime errors for one venue, emits a VENUE_RECONCILIATION_FAILED warning and continues with the remaining venues, so one unreachable venue degrades the start rather than blocking it. The critical count is returned to the caller, which decides whether to log a degraded start; the design note in the module is explicit that this lets an operator override a stuck startup instead of needing a manual database edit.

4. Reconciler failure becomes a circuit breaker

This is a separate mechanism from the engines above, which catch, log and continue and never arm anything themselves. ReconcilerBreakerBridge subscribes to four state-surface reconcilers from the shared library, position, balance, custody and on-chain, and on a breaker fire it emits a CIRCUIT_BREAKER_OPEN alert and, when the breaker's configured action is BreakerAction.KILL_ALL, arms the kill switch with KillSwitchProvenance.BREAKER_AUTO. The bridge owns no scheduling and no reconcile logic of its own, by its own docstring; it is purely the wire between a reconciler verdict and the halt bus. Failures inside the callback are caught narrowly so that a fault in the bridge can never propagate back into the reconciler. The full arm-and-halt path from there is §06, 6.4.

There are two independent mechanisms: an automatic circuit that reacts to position health, and an operator kill switch delivered over the event bus with per-archetype halt semantics. They are separate on purpose; one does not depend on the other being healthy.

The automatic circuit

The design point is that the response is graded. A position drifting toward its health floor gets a pause or a staged reduction; only genuine proximity to liquidation triggers a flash close. A binary stop-everything breaker is both more likely to fire spuriously and more expensive when it does. _mid_loop_recovery exists because the dangerous state is not "halted"; it is "halted halfway through a multi-leg action", and that needs an explicit path back.

The operator kill switch

Arming is an event on the bus, so it reaches every running instance without a deploy and without the strategy process needing to poll. Halting is per archetype rather than global, so one strategy can be stopped while others continue, and ArchetypeHaltBehaviour lets each archetype declare what halting means for it, because "stop trading" is not the same instruction for a market-making book as for a basis position that must stay hedged.

Kill-switch scope

Arming targets are a closed enum, KillSwitchId, and the granularity is the point: a venue in trouble should not require halting strategies that never touch it, and an archetype behaving badly should not require halting a venue other archetypes depend on. A proportionate response is far more likely to be used early.

Two properties of that vocabulary carry most of the operational meaning. First, scope granularity runs global, archetype, venue, asset group, treasury source and wallet, and there is deliberately no per-client switch; client separation is enforced structurally elsewhere (§11) rather than by a halt. Second, recovery is per breaker, not uniformly manual. Protective arming is always allowed to happen on its own; whether resuming does depends on the breaker's configured BreakerRecoveryMode. A breaker configured AUTO_COOLDOWN is disarmed by risk/recovery_loop.py's BreakerRecoveryEngine once its cooldown or hard timeout elapses; a breaker configured MANUAL_UNKILL is never cleared by that ticker and waits for an operator. The direction is what is invariant: automatic movement is only ever toward safety.

What halting means, per archetype

ArchetypeKillSwitchSubscriber.on_armed() selects an ArchetypeHaltBehaviour from the arm metadata by a declared precedence: an explicit slow-unwind override wins, otherwise a maximum-drawdown breach reason selects a fast unwind, otherwise an open cross-venue position selects a delta hedge, otherwise the default is to stop new decisions only. The uniform rule underneath all four, in the guard's own words, is to pause target-tracking rather than to fight back to target. Halting is not flattening; flattening is a separate, invoked plan (§06, 6.4).

The automatic circuit is a decision function, not an actor

LiquidationProximityCircuit.evaluate() returns a ProximityDecision. It does not arm the bus, place an order or unwind anything itself; the caller acts on the decision. Keeping the grading logic pure is what makes it testable against a health alert without a live position, and it is why the set of code paths that can actually halt live trading stays small enough to audit.

How you would halt it, concretely

Three levels, in increasing severity: publish a kill-switch armed event for the archetype (halts new decisions, honouring the archetype's declared halt behaviour); set the instance's capital budget to zero in configuration (prevents new exposure while leaving the position monitored); or stop the process (the position remains, and nothing is monitoring it, so this is the least safe option, not the most). Under the managed service the first is what we use, and the operational console exposes it as a single action.

Risk: drawdown, leverage, delta and position caps

Risk rules sit between a strategy's intent and its execution. A rule that fires can warn, or it can block the instruction and emit a rejection event, so a blocked instruction is a recorded fact rather than a silence.

The limit set

class RiskLimits: # strategy_service/risk/models.py, per client, per slot max_position_size max_position_value max_gross_exposure max_net_exposure max_single_instrument_exposure max_venue_exposure max_leverage min_margin_ratio # plus the VaR fields # the warn tier sits alongside each hard cap max_leverage_warning max_drawdown_pct max_drawdown_warning_pct

Enforcement is risk/core/pre_trade_check_engine.py's PreTradeCheckEngine, which evaluates the typed trigger set, MaxGrossExposureTrigger, MaxNetExposureTrigger, MaxPositionSizeTrigger and MaxLeverageTrigger, against the declared limits. The consequence vocabulary is a closed four-way set, BLOCK, SCALE_DOWN, MONITOR and TEST_ONLY, with BLOCK taking precedence, then SCALE_DOWN, then TEST_ONLY, then MONITOR.

Why every limit has a warning tier

A single hard threshold gives no time: you are either inside it or already in breach, and the corrective trade then has to happen at the worst possible moment. The warning tier exists so exposure can be reduced while the market is still orderly. The breach tier is the backstop, not the plan.

Delta neutrality

For strategies meant to be market-neutral, residual delta is tracked as a composite across every leg and every venue rather than per position. position/core/risk_group_aggregator.py's RiskGroupAggregator._build_group_summary() groups positions by underlying and folds their signed quantities into one net delta per group, surfaced as a RiskGroupSummary. Neutrality is therefore a measured property of the book rather than an assumption inherited from the strategy's design. A carry position is only carry while it stays hedged, and drift is what turns it into a directional position nobody chose, which is why the composite is monitored continuously rather than checked at entry.

The hedge itself is sized rather than mirrored. engine/strategies/v2/carry_and_yield/dynamic_hedge_ratio.py's compute_dynamic_hedge_ratio() is a pure function that sizes the short leg against the staked quantity, the peg rate and the margin haircut the venue applies, and it rebalances only once drift crosses a declared threshold in basis points rather than on every tick. Sizing against the haircut rather than against gross notional is what keeps the hedge from consuming more margin than the exposure it offsets: two trades can produce the same net delta while leaving very different gross exposure and margin requirement behind, and the cheaper-looking one is often the one that increases fragility.

What is a threshold rule and what is an optimiser

The haircut-aware sizing and the hysteresis band above are real, and so is KillSwitchDecision.DELTA_NEUTRAL_EXIT, which its own docstring describes as the cheapest exit because it avoids one-sided market impact. What does not exist is a general optimiser that scores candidate hedges by added leverage and picks the minimum. Reducing an existing position in preference to opening an offsetting one is the design intent and the shape of the rules above; it is not implemented as a leverage-minimisation search.

Book-level overlays

Some controls apply above the level of any single position. portfolio_allocator/guard_rails.py's apply_guard_rails() is the cross-strategy layer: a maximum weight per sleeve, a correlation cap, family and category diversification caps, a turnover cap and a no-trade band that suppresses rebalancing below a drift threshold. A vol-target overlay lets a directional archetype size to a target volatility rather than a fixed notional, so exposure contracts automatically when realised volatility rises, and the hysteresis-band pattern is confirmed at the position level for peg-tracking hedge ratios.

The book-level beta hedge is specified and not built, and the code says so itself: engine/strategies/v2/carry_and_yield/funding_dispersion.py's module docstring enumerates which of its research overlays exist in production and records that residual market beta is intended to be hedged at the book level with no such overlay in place. Reading that docstring is the reliable way to see the current split between the overlays that run and the ones that are designed.

Position caps

Notional ceilings apply per position and per slot through the pre-trade engine above, so a single archetype cannot consume the book by rule. The stronger structural claim, that per-slot trading wallets (§11) bound exposure by construction so a slot cannot trade capital it was never given, is the design intent rather than today's enforcement: TradingWalletConfig's get_trading_wallet() lookup has no call sites outside the contracts package and its tests, and capital_budget_amount is carried through the data plane without a guard that rejects on it. The rule-based ceiling is what is actually enforced.

Where Copper and Ceffu actually sit

Our code talks to Copper and to Ceffu. Collateral posted into Copper custody is mirrored onto the exchange by Copper's own mirroring capability so it can be traded without ever leaving custody, the property that matters for counterparty risk. For Binance the same role is played by Ceffu's off-exchange settlement. The consequence worth understanding is that a move between two venues under the same custodian is a mirroring instruction to that custodian and no coin moves at all; a move that crosses custodians unmirrors on one side, settles on-chain between the two, and re-mirrors on the other. The instruction the strategy emits is TransferInstructionV2, which names none of this, and position and P&L tracking is identical whether the collateral is mirrored or held directly, because the mirrored balance is what is tracked.

Where a venue accepts off-exchange settlement, collateral never moves to the venue at all: it stays with the custodian and the venue is granted a mirror credit against it. The custodian settles the mirror on its own schedule rather than moving collateral on every position change, so exposure at the venue can change without a corresponding transfer for every adjustment. Position and P&L tracking is identical whether the collateral is mirrored or held directly, because the mirrored balance is what is tracked.

Where the mirroring surface stands

The custody-provider side is scaffolded with real methods and a real settlement model described in their own docstrings, and the venue-side API those methods depend on is not yet available, so execution_service/custody/ceffu.py's off-exchange-settlement mirror-balance and mirror-move methods raise rather than executing. The property to hold on to is that this is a custodian mechanism rather than a separate integration on our side: you will find copper.py and ceffu.py in the execution service and no vendor-specific mirroring code path, and that is by design.

Funding follows the same binding backwards through the rail set above: a CEX_DEPOSIT or DEFI_DEPOSIT targets the specific (client_id, slot_label) wallet that will trade it rather than a shared pool divided afterwards, so which route a client's capital enters through is a property of which wallet it targets rather than a separate routing decision layered on top.

Venue allocation follows from the same binding. Feeding an external strategy in

If you wanted to run your own strategy on this infrastructure, the integration surface is small and precisely defined: consume the tick, emit one of the 16 instruction types with a valid envelope, and everything downstream applies unchanged.

What an external strategy must provide, and what it gets for free

The contract is: your archetype is registered, receives ticks from V2EngineOrchestrator, and returns instructions.

# What you provide 1. An archetype module that evaluates on each tick and returns zero or more StrategyInstructionV2 (the union of the 16 types, see §04) 2. Because the envelope carries eligible_venues and execution_policy_ref, your strategy declares where it may trade and which policy should work its orders, without needing to know how either is implemented. The practical consequence

A strategy idea becomes a config file and one module implementing one interface. It inherits the risk, reconciliation, attribution and operational estate on its first tick rather than needing them built. That is the same route our own archetypes take; there is no separate internal path.

Research, backtests and P&L attribution

Under the ongoing arrangement you can bring ideas rather than only receive results. Backtests launch through the same contract as live runs, which is what makes a backtest result meaningful rather than indicative.

Same code pathA backtest runs the identical engine, contract and ledger as live, not a separate simulator
One launch contractBacktest, experiment and live launches route through the same deployment API
Promotion is a ladderCandidate → paper → early live → live, with pre-flight gates at each step
How a submitted idea becomes a tested result, and what you would see

The property that makes this worth doing is that paper and batch runs are required to agree with each other trade for trade. Because the same orchestrator, the same instruction contract and the same ledger writers serve batch, paper and live, a backtest is a rerun of the production program over historical data rather than a model of it. A result therefore carries over to live behaviour, subject only to fills.

# What a research contribution looks like in practice 1. You describe the idea, a parameter variation on an existing archetype, or a new decision rule 2. It becomes a config (a variation) or a module (a new rule), per §14 3. It launches as a backtest through the deployment API, against the same history and feature versions our own research uses 4. Results come back as the standard ledgers and attribution, so they are directly comparable with live performance, not a separate report format 5. If it earns promotion it climbs the ladder: candidate, paper, early live, live, with pre-flight gates at each step

What you would see is the attribution surface from §13 applied to your idea: P&L split across decision, execution and funding, per venue and per leg. That split is usually the interesting part, because it separates "the idea was right" from "the idea was implementable".

Fill fidelity is declared, and clamps in one direction

A backtest is only as honest as its fill assumptions, so the system records what data quality a given venue, instrument and period actually had, and never claims a better fill model than the data supports.

class ExecutionFidelityTier(StrEnum): # unified_api_contracts/canonical/crosscutting/execution_fidelity.py L2_TICK # full depth and trades CANDLE_BOOK_COLS # bars with book-derived columns OHLC_BAR # open, high, low, close only # ordering: L2_TICK > CANDLE_BOOK_COLS > OHLC_BAR def execution_fidelity(...) -> ExecutionFidelityTier # the tier available for this (venue, instrument_type) cell

A strategy may request a maximum tier and the engine clamps down to whatever execution_fidelity() returns for the cell, never up. There is deliberately no trade-tape-only tier: without book state the matcher falls back to bar fill, which is what a trades-only venue resolves to. The clamp direction is the safeguard, because an optimistic fill model flatters a backtest in exactly the way that is hardest to notice. Where finer data exists it is used; where it does not, the model steps down a tier rather than refusing to run, so an instrument with no tick history is still testable with its fills marked as the coarser estimate they are.

Ledgers and attribution dimensions

The same window can be read three ways at once: as it actually filled, as it would have filled at the benchmark reference price, and as the batch rerun produced it. That is what turns "execution cost us X" into a measured quantity rather than an estimate. P&L decomposes by venue, account, client, instrument and strategy slot, the same identity from §02, which is what lets a number in a client report be traced back to the instructions that produced it.

Two different high-water marks, worth not conflating

Inside the engine, engine/core/components/pnl_monitor.py's PnLMonitor carries a running high-water mark seeded at initial capital and raised whenever total equity exceeds it. That is a drawdown measure, and drawdown against it is what the risk limits in §10 test. The fee-bearing high-water mark that governs a performance fee is a different quantity: it has to be computed on a flow-adjusted basis so that a subscription or a redemption neither creates nor erases a fee position, and that calculation belongs to the client-accounting layer rather than to this repository. Reading the engine's equity-based mark as the fee mark would be a mistake.

How strategy alpha is separated from execution alpha

That separation is not a reporting convention applied afterwards; it is how the backtest is constructed. A benchmark fill is the answer to a single question: if this order filled with zero market impact at the benchmark reference price, what would the fill look like? The reference is defined per instruction and per algo, mid at arrival for a sweep, the time-weighted mid over the window for a TWAP, pool mid at the target block for a protected swap. One contract defines it, and two isolations use it:

# The same benchmark reference, used two ways Strategy isolation benchmark fills ARE the fills. Zero execution alpha by construction, so what remains is the strategy's own edge. Runs against pipeline history with no execution stack at all. Execution isolation a matching engine fills against real historical book state, and the benchmark is the reference it is measured against. What remains is execution alpha: slippage, fees, timing.

The consequence is that a strategy's measured edge does not silently inherit an execution choice it did not make, and execution quality is not credited or blamed for market direction. The fill engine is a pure function, the same inputs produce bit-identical outputs, so the strategy-side number is reproducible rather than approximately repeatable.

What that yields per order is the execution residual itself: the difference between the live fill and the benchmark fill, separated into slippage against the benchmark price and the fee surprise (actual against modelled). Those are the two components that tell you whether an algo is paying away its edge, and they are attributed per venue and per leg alongside the strategy-layer decomposition.

Worth agreeing in advance

If a contributed idea works, ownership and commercial treatment are better settled before the contribution than after it. We would rather raise that now, while it is hypothetical, than negotiate it about something specific that already works.

Three surfaces, tracked apart

A venue counts as supported only when three separate things hold: its market data is captured, an execution path reaches it, and its positions can be read back. They are tracked independently rather than one being inferred from another. The read surface has its own per-venue, per-mode capability record (§13) for a specific reason: being able to act without being able to see is strictly worse than the reverse, because the instruction lands, the position changes, and nothing afterwards can confirm it or detect drift.

The two surfaces behave differently by construction. Centralised venues are broad: the exchange adapter is generic over any supported exchange identifier, so most are reachable without a dedicated module, and dedicated adapters exist only where authentication is bespoke. On-chain venues are not generic, and that is where the remaining wiring sits: connectors exist ahead of the paths that call them, and the gap is being closed venue by venue. The measurement of that gap is a caller-graph sweep asking whether anything on a production path calls a connector at all, which is a different question from whether the connector works, and it now runs as an automated gate rather than a manual count, so the next figure is a build output.

Signal leasing: a second external surface

§03 describes one way an outside party reaches what this service produces: hand the decision to execution-service and let it trade. This is the other. Odum keeps execution entirely, and a counterparty subscribes to the signal itself and self-executes.

A counterparty is not a clientNo portfolio allocation, no share-class mapping, no capital routed through our infrastructure
Webhook push, REST pull as fallbackSigned, retried, and both paths write to the same audit trail
Payload depth is entitled per counterpartyThree tiers, one field, with the richest tier bounded by an enforced cap
"Counterparty" is a distinct entity type

A signal-leasing Counterparty is a different model from a ClientDefinition. Counterparties pay a per-slot subscription to receive emitted signals; they have no portfolio allocation, no share-class mapping and no capital routed through Odum's infrastructure at all. What travels to them is the archetype's directional intent and sizing, not a trade, not custody and not a fill. The model carries id, status, endpoint, allowed_slots, hmac_secret_ref and rate_limit_ref, and lives in unified_api_contracts/internal/domain/signal_broadcast/counterparty.py.

How a counterparty is onboarded, and how an emission reaches it

Onboarding is a registry row plus a secret, with no strategy-service change. cli/service_entry.py's _get_config() reads active_counterparties() from the contracts registry once at boot and hands the result to the signal-broadcast reloaders, so a counterparty becomes reachable by carrying CounterpartyStatus.ACTIVE together with a real endpoint and secret reference. The registry is seeded with two placeholder rows held at SUSPENDED ahead of the September 2026 window, and real endpoints and Secret Manager references are injected at deploy time rather than committed.

Emissions are pushed to the counterparty's own webhook endpoint first, signed with HMAC-SHA256, retried with exponential backoff on 5xx and connection errors and abandoned on 4xx other than 408 and 429. The REST-pull surface below exists for reconciliation: a counterparty that missed a push, or that wants to replay a window, pulls the same emissions back out of a bounded in-memory ring buffer and can acknowledge out of band. Both paths write to the same audit trail, so "did they receive it" has one answer regardless of which route delivered it.

Auth here is per counterparty, not the platform's shared mechanism

Every request carries Authorization: Bearer <jwt>, an HS256 token signed with that counterparty's own secret, resolved from Secret Manager via hmac_secret_ref and never held as a literal. The router decodes the token against the exact counterparty named in the request and rejects a token that does not match, so one secret buys access to one counterparty's own data and never another's.

Emission dispatch, rather than the REST-pull request itself, is token-bucket limited per (counterparty_id, strategy_id) against a named RateLimitConfig profile resolved from Counterparty.rate_limit_ref: default at 10 per second with burst 10, minimal at 5 with burst 5, and burst at 25 with burst 50. A counterparty at its cap is not dropped silently; the emitter records the rate-limited outcome and it appears in delivery health.
