01

What this repository is, and what it isn't

This service decides. It consumes features and market state, evaluates archetypes on each tick, sizes and hedges, and emits typed instructions. It does not connect to venues, work orders into the market, or move funds itself — those are execution-service concerns, reached through the contracts in §02.

It decidesArchetype evaluation, sizing, hedge ratios, risk vetoes, position monitoring, P&L attribution
It does not executeNo venue connectivity, no order working, no signing. It emits intent; execution-service realises it
One tick interfaceEvery archetype in every family implements the same interface, which is what makes the rest of this document short
Layout, boundaries, and the one rule that governs both
499Python modules
102kLines of code
11Instruction types emitted
19API route modules

The top-level packages map directly onto responsibilities, and the names are literal:

engine/ archetype implementations + the V2 orchestrator that ticks them configs/ one YAML per strategy instance, plus configs/defaults/ per family position/ position monitor, treasury monitor, reconciliation, NAV, margin health risk/ pre-trade risk gates and limit evaluation pnl/ attribution — decision vs execution vs funding circuit_breakers/ automatic protective actions (see §04) portfolio_allocator/ capital allocation across instances compliance/ attestation and evidence trail allocation_sizer.py position sizing against capital budget transfer_coordinator.py intra-client rebalance netting (see §05) archetype_kill_switch_subscriber.py halt semantics (see §04) config_reloaders.py typed hot-reload of configuration api/ read + control surfaces (see §06)

The governing rule is the tier model: imports only ever point downward, and no service imports another service. This repository depends on the shared library and the contracts package, and on nothing else in the estate. That is why it can be read in isolation — and why the set of things it needs from outside is finite and enumerable rather than a matter of discovery.

What is deliberately not here

Execution algorithms and order routing, venue adapters and connectivity, custody signing, market-data capture, and feature computation all live in other services. Where this repository needs one of them it holds an interface, not an implementation. Those seams are the subject of §02 and §05.

02

The strategy → execution contract

This is the part most likely to matter to you, because it is the boundary your side would integrate against. Every strategy in every family emits one of eleven instruction types, all sharing a common envelope. The envelope is where the interesting design sits.

One envelopeIdentity, urgency, deadline, policy reference, attestations, eligible venues, constraints
Eleven subtypesTrade, Swap, Lend, Borrow, Stake, Unstake, Quote, Transfer, Bridge, Atomic, Cancel
Declares intent, not methodThe strategy says what it wants and where it may go; execution decides how
The envelope, all eleven subtypes, and what the design guarantees

The envelope — every instruction carries this

class StrategyInstructionEnvelope(BaseModel): instruction_id: str emitted_at_utc: datetime identity: StrategyInstanceIdentity urgency: Urgency = Urgency.MEDIUM deadline_utc: datetime | None = None execution_policy_ref: str | None = None # names a policy; does not contain it attestations: dict[str, str] = {} # compliance trail correlation_id: str | None = None eligible_venues: list[str] = [] # where it MAY go venue_constraints: dict[str, VenueConstraints] = {} venue_routing_mode: VenueRoutingMode = VenueRoutingMode.SOR_AT_EXECUTION target_venue: str | None = None chain: str | None = None class VenueConstraints(BaseModel): max_notional_usd: Decimal | None = None min_liquidity_usd: Decimal | None = None fee_tier: str | None = None max_slippage_bps: int | None = None

Three fields carry most of the architectural meaning. eligible_venues plus venue_constraints say where an instruction is permitted to be worked and under what limits; venue_routing_mode defaults to SOR_AT_EXECUTION, meaning the venue choice is made at execution time rather than by the strategy; and execution_policy_ref names an execution policy without containing it. The strategy therefore expresses intent and permission, and never expresses method. That separation is enforced by the type, not by convention.

Position and target instructions

class TradeInstruction(StrategyInstructionEnvelope): action: Literal[TRADE] target_position_units: Decimal # a TARGET, not a delta — idempotent by design target_instrument: str direction: Literal["LONG", "SHORT", "FLAT"] | None = None max_price: Decimal | None = None min_price: Decimal | None = None stop_loss_price: Decimal | None = None take_profit_price: Decimal | None = None class SwapInstruction(StrategyInstructionEnvelope): action: Literal[SWAP] in_asset: str out_asset: str in_amount: Decimal min_out_amount: Decimal # slippage bound expressed as an outcome route_hint: str | None = None mev_policy_ref: str | None = None class QuoteInstruction(StrategyInstructionEnvelope): action: Literal[QUOTE] instrument: str reference_price: Decimal half_spread_bps: int max_inventory_abs: Decimal skew_on_inventory: bool = True refresh_cadence_ms: int = 1000

target_position_units is worth pausing on: instructions express a target rather than a delta. Re-emitting the same instruction is therefore idempotent, and a missed or duplicated message cannot compound a position. This is the single most useful property to know when integrating.

DeFi leg instructions

class LendInstruction(StrategyInstructionEnvelope): action: Literal[LEND] protocol: str asset: str target_supplied_amount: Decimal min_apy_bps: int | None = None class BorrowInstruction(StrategyInstructionEnvelope): action: Literal[BORROW] protocol: str asset: str target_debt_amount: Decimal max_borrow_apy_bps: int | None = None collateral_health_min: Decimal | None = None class StakeInstruction(StrategyInstructionEnvelope): action: Literal[STAKE] protocol: str asset: str target_staked_amount: Decimal lst_asset: str | None = None class UnstakeInstruction(StrategyInstructionEnvelope): action: Literal[UNSTAKE] protocol: str asset: str amount: Decimal exit_queue_ok: bool = True # whether an exit queue is acceptable

Capital movement instructions

class TransferInstructionV2(StrategyInstructionEnvelope): action: Literal[TRANSFER] asset: str venue_from: str venue_to: str target_balance_at_destination: Decimal # an OUTCOME, not a route max_cost_bps: int | None = None class BridgeInstructionV2(StrategyInstructionEnvelope): action: Literal[BRIDGE] asset: str chain_from: str chain_to: str target_balance_at_destination: Decimal bridge_hint: str | None = None

Note what is absent: neither carries a rail, a custodian or a mechanism. The strategy asks for a balance to exist at a destination within a cost bound; how that is achieved — an internal venue transfer, an exchange withdrawal, an on-chain send through custody — is resolved downstream. §05 covers what actually happens.

Multi-leg and cancellation

class AtomicLeg(BaseModel): leg_index: int action: InstructionActionV2 instrument: str side: Literal["BUY", "SELL"] | None = None size_units: Decimal | None = None venue: str | None = None weight: Decimal | None = None params: dict[str, str] = {} class AtomicInstruction(StrategyInstructionEnvelope): action: Literal[ATOMIC] legs: list[AtomicLeg] execution_mode: AtomicExecutionMode leader_leg: int | None = None # which leg goes first hedge_deadline_ms: int | None = None # how long the book may sit unhedged compensation_policy: CompensationPolicy | None = None # what happens if a leg fails balance_mode: str | None = None max_total_slippage_bps: int | None = None class CancelInstruction(StrategyInstructionEnvelope): action: Literal[CANCEL] cancel_instruction_id: str cancel_scope: Literal["SINGLE", "ALL_FOR_STRATEGY_INSTANCE"] = "SINGLE"

AtomicInstruction is how a basis trade is expressed as one unit: the staking leg and the hedge leg travel together, with a declared leader, a deadline on how long the position may sit unhedged, and a compensation policy if a leg fails. A partially-filled multi-leg structure is the central operational risk in basis trading, and it is handled at the contract level rather than in strategy code.

Strategy instance identity — what every instruction is stamped withReference
class StrategyInstanceIdentity(BaseModel): family: StrategyFamily archetype_id: StrategyArchetype archetype_build_version: str strategy_instance_id: str slot_version: int = 1 config_hash: str # the exact config that produced this decision config_version: int client_id: str share_class: ShareClass env: Literal["prod", "paper", "canary", "dev"] = "prod" holding_wallet: str | None = None wallet_id: str = "" class StrategyInstanceDefinition(BaseModel): strategy_instance_id: str archetype_id: StrategyArchetype family: StrategyFamily client_id: str capital_budget_amount: Decimal # the instance cannot exceed this capital_budget_share_class: ShareClass share_class: ShareClass env: Literal["prod", "paper", "canary", "dev"] = "prod" created_at_utc: datetime created_by: str retired_at_utc: datetime | None = None retired_reason: str | None = None slot_version: int = 1 holding_wallet: str | None = None wallet_id: str = ""

Because config_hash and archetype_build_version ride on every instruction, any decision can be traced back to the exact code and configuration that produced it, and a run can be replayed from its manifest. This is the mechanism behind the batch/live equivalence property — the same identity flows through a backtest, a paper run and a live run.

04

Halting it: breakers and kill switch

There are two independent mechanisms: an automatic circuit that reacts to position health, and an operator kill switch delivered over the event bus with per-archetype halt semantics. They are separate on purpose — one does not depend on the other being healthy.

AutomaticLiquidationProximityCircuit — seven graded responses to a health alert
Operator-drivenArchetypeKillSwitchSubscriber — arm/disarm per archetype over the bus
Graded, not binaryResponses range from an oracle buffer through partial unwind to flash close
Both mechanisms, their decision surfaces, and how you would drive them

The automatic circuit

class LiquidationProximityCircuit: def evaluate(self, alert: DefiAlert) -> ProximityDecision: ... # graded responses, selected by how close the position is to liquidation _oracle_buffer() # widen tolerance for oracle lag; take no position action _position_pause() # stop opening; hold what is held _partial_unwind() # reduce exposure toward the health target _hedge_failover() # re-establish the hedge via an alternate venue _flash_close() # exit now, accept slippage _mid_loop_recovery() # resume safely after an interrupted action class ProximityDecision: ... # the chosen action + its rationale class ProximityAction(StrEnum): ...

The design point is that the response is graded. A position drifting toward its health floor gets a pause or a partial unwind; only genuine proximity to liquidation triggers a flash close. A binary stop-everything breaker is both more likely to fire spuriously and more expensive when it does. _mid_loop_recovery exists because the dangerous state is not "halted" — it is "halted halfway through a multi-leg action", and that needs an explicit path back.

The operator kill switch

class ArchetypeKillSwitchSubscriber(KillSwitchSubscriber): def on_armed(self, event: KillSwitchArmedEvent) -> None: ... def on_disarmed(self, event: KillSwitchDisarmEvent) -> None: ... def is_archetype_halted(self, archetype: str) -> bool: ... def halt_behaviour(self, archetype: str) -> ArchetypeHaltBehaviour | None: ... class ArchetypeHaltBehaviour(StrEnum): ... # what "halted" means for this archetype

Arming is an event on the bus, so it reaches every running instance without a deploy and without the strategy process needing to poll. Halting is per archetype rather than global, so one strategy can be stopped while others continue — and ArchetypeHaltBehaviour lets each archetype declare what halting means for it, because "stop trading" is not the same instruction for a market-making book as for a basis position that must stay hedged.

How you would halt it, concretely

Three levels, in increasing severity: publish a kill-switch armed event for the archetype (halts new decisions, honouring the archetype's declared halt behaviour); set the instance's capital budget to zero in configuration (prevents new exposure while leaving the position monitored); or stop the process (the position remains, and nothing is monitoring it — so this is the least safe option, not the most). Under the managed service the first is what we use, and the operational console exposes it as a single action.

Capital, collateral and Copper

The strategy never names a rail. It asks for a balance to exist somewhere, and a layered set of coordinators and adapters resolves that into either an exchange transfer or an on-chain movement signed through custody. Copper sits at the custody end, and its ClearLoop service is what lets collateral be traded at a venue without leaving custody.

Netted before emittedIntraClientRebalanceCoordinator nets offsetting requests per pair before any intent is produced
One entry pointTransferCoordinator validates, enforces client isolation and de-duplicates
Rail chosen lastCompositeTransferAdapter routes exchange moves to venue APIs and on-chain moves to custody
The full path from a strategy's rebalance request to funds arriving

Wallet and transfer vocabulary

class WalletType(StrEnum): FUNDING # where deposits land; not directly tradeable TRADING # where orders are placed from SPOT # separate spot wallet, on venues that have one UNIFIED # single-account venues class TransferType(StrEnum): ON_CHAIN # blockchain transfer, signed via custody or local key. DeFi→DeFi same chain, DeFi→CeFi deposit, CeFi→DeFi withdrawal. Minutes; gas applies. CEX_WITHDRAWAL # exchange withdrawal to an external address, via CCXT. CeFi→CeFi cross-exchange, or CeFi→DeFi. Minutes to hours; withdrawal fees apply.

Custody is an interface, not a vendor

class CustodyProvider(Protocol): async def sign_transaction(wallet_id, chain, raw_tx) -> SignedTransaction async def get_balance(...) async def create_transfer(...) async def list_wallets(chain=None) -> list[dict[str, str]] async def health_check() -> CustodyHealth # get_custody_provider(config) resolves by name: mock · local_key · cloud_kms · copper · ceffu

Because custody is a Protocol with five methods, adding or changing a custodian is a new implementation plus a configuration value — not a change to any strategy or execution path. The Copper implementation is execution_service/custody/copper.py, and it signs, polls for completion, reads balances, creates transfers, lists wallets and reports health.

Where Copper and ClearLoop actually sit

Our code talks to Copper. Collateral is posted into Copper custody, and Copper's ClearLoop service mirrors that collateral onto the exchange so it can be traded without ever leaving custody — which is the property that matters for counterparty risk. ClearLoop is therefore Copper's mechanism rather than a separate integration on our side: you will find copper.py in the execution service and no ClearLoop-specific code path, and that is by design. The instruction the strategy emits is TransferInstructionV2, which names neither.

Client isolation — the guarantee, and where it is enforcedReference
class TransferCoordinator: """Single entry point for all TransferIntent events.""" def execute(self, intent: TransferIntent) -> TransferResult def validate_intent(self, intent: TransferIntent) -> None def register_handler(self, transfer_type, handler) -> None class CrossClientTransferForbiddenError(RuntimeError): ...

Funds cannot move between clients: every transfer is scoped to a single client_id, and an intent that would cross that boundary raises rather than executing. The guarantee is structural — it is not a policy check that could be configured off, and there is no code path that expresses a cross-client movement. Each client also runs in its own process. The coordinator additionally holds an idempotency cache, so a replayed intent returns the original result instead of moving funds twice.

07

Feeding an external strategy in

If you wanted to run your own strategy on this infrastructure, the integration surface is small and precisely defined: consume the tick, emit one of the eleven instruction types with a valid envelope, and everything downstream applies unchanged.

Implement one interfaceEvaluate on tick, return instructions. The orchestrator handles lifecycle
Inherit the estateRisk gates, position monitoring, reconciliation, attribution and breakers apply automatically
Nothing bespokeAn external strategy is not a special case — it is another archetype in the registry
What an external strategy must provide, and what it gets for free

The contract is: your archetype is registered, receives ticks from V2EngineOrchestrator, and returns instructions.

# What you provide 1. An archetype module that evaluates on each tick and returns zero or more StrategyInstructionV2 (the union of the 11 types) 2. A config YAML declaring instruments, thresholds and capital budget, validated against the typed schemas in §03 3. A registry entry naming the archetype and its family # What applies without you writing it · Pre-trade risk gates and limit checks · Position monitoring and venue reconciliation · Capital budget enforcement per instance · P&L attribution by decision/execution/funding · Circuit breakers and kill-switch semantics · Compliance attestation on every instruction · Execution algorithms and venue routing · Transfer netting and custody routing · The promotion ladder: candidate → paper → live

Because the envelope carries eligible_venues and execution_policy_ref, your strategy declares where it may trade and which policy should work its orders, without needing to know how either is implemented. And because instructions express targets rather than deltas, your strategy does not have to track what has already been filled to remain correct.

The practical consequence

A strategy idea becomes a config file and one module implementing one interface. It inherits the risk, reconciliation, attribution and operational estate on its first tick rather than needing them built. That is the same route our own archetypes take — there is no separate internal path.

08

Asset-group agnosticism and expansion

The same engine, contract and ledger serve every asset group. This is the property that makes expansion a configuration and adapter exercise rather than a new system, and it is a property of the ongoing platform rather than of any static snapshot.

One engine, five asset groupsDeFi, CeFi, TradFi, sports and prediction markets run the same tick loop and contract
Eight families presentCarry and yield, arbitrage, statistical arbitrage, volatility, market making, directional, liquidity provision, ML-driven
Config-shaped, not fork-shapedPer-asset-group typed config blocks rather than per-asset-group codebases
How one engine serves five asset groups, and what expansion costs

The mechanism is visible in the configuration schemas from §03: DefiRiskConfig, CexRiskConfig, MlRiskConfig and SportsRiskConfig are per-asset-group blocks against a common engine, not separate engines. The same pattern runs through attribution (DefiAttributionConfig, MlAttributionConfig) and mode (DefiModeConfig, MlModeConfig). Adding an asset group adds blocks and an adapter; it does not fork the engine.

What each direction of expansion actually touchesReal work in every row — the point is which layers, not that it is free
DirectionWhat changesWhat does not
Another instrumentA universe entry, once capture covers itEngine, contract, risk, attribution, ledgers
Another venueAn adapter, a registry entry, collateral calibration, a cutoverThe instruction contract and everything above it
Another LST or protocolA collateral-matrix entry, a rate reader, rebasing reconciliationThe staked-basis archetype itself
Another chainRPC, gas and settlement handling; the structure already runs on two chainsStrategy logic and instruction shape
Another archetypeOne module and a config, per §07The entire operational estate
Another asset groupTyped config blocks and venue adapters; TradFi additionally brings clearing and reportingThe engine, the tick loop and the ledger model

This is the concrete answer to why the strategy is not a standalone program. It is agnostic because the things it would otherwise hard-code — venue, asset class, execution method, custodian — are all resolved outside it. That agnosticism is exactly what a static carve-out cannot reproduce, because a snapshot fixes each of those choices at the moment it is taken.

09

Contributing research and backtests

Under the ongoing arrangement you can bring ideas rather than only receive results. Backtests launch through the same contract as live runs, which is what makes a backtest result meaningful rather than indicative.

Same code pathA backtest runs the identical engine, contract and ledger as live — not a separate simulator
One launch contractBacktest, experiment and live launches route through the same deployment API
Promotion is a ladderCandidate → paper → early live → live, with pre-flight gates at each step
How a submitted idea becomes a tested result, and what you would see

The property that makes this worth doing is that paper and batch runs are required to agree with each other trade for trade. Because the same orchestrator, the same instruction contract and the same ledger writers serve batch, paper and live, a backtest is a rerun of the production program over historical data rather than a model of it. A result therefore carries over to live behaviour, subject only to fills.

# What a research contribution looks like in practice 1. You describe the idea — a parameter variation on an existing archetype, or a new decision rule 2. It becomes a config (a variation) or a module (a new rule), per §07 3. It launches as a backtest through the deployment API, against the same history and feature versions our own research uses 4. Results come back as the standard ledgers and attribution — so they are directly comparable with live performance, not a separate report format 5. If it earns promotion it climbs the ladder: candidate, paper, early live, live — with pre-flight gates at each step

What you would see is the attribution surface from §06 applied to your idea: P&L split across decision, execution and funding, per venue and per leg. That split is usually the interesting part, because it separates "the idea was right" from "the idea was implementable".

Worth agreeing in advance

If a contributed idea works, ownership and commercial treatment are better settled before the contribution than after it. We would rather raise that now, while it is hypothetical, than negotiate it about something specific that already works.
