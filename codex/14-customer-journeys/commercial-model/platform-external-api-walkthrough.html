How to read this

This document is deliberately long and deliberately collapsed. Nothing is hidden — everything is one click away — but you should never have to scroll past a section you do not care about.

The three conventions worth knowing before you start
Collapse anythingSections collapse. Inside coverage, an asset group collapses, then a venue, then an instrument type. Fold away what you are not evaluating
Status is per-sectionEvery section carries live, partial or planned — against one test: can something on a production path actually reach it
Numbers carry provenanceA figure is either measured with its date and denominator, or marked pending. There is no third category
The one convention that matters most

Coverage percentages are meaningless without their denominator, so every one here states what it is over. "80% of venues" and "80% of venue-and-data-type pairs" are different claims, and the second is the honest unit because a venue is only useful for the data types it actually carries.

Where a number has not been measured yet it says pending rather than carrying an estimate. An estimate that survives into an integration plan becomes a commitment nobody agreed to.

How you connect

live

You call the same contracts our services call. There is no separate "external" API with reduced fidelity, because a second API surface is a second thing to keep true.

The integration model, and why it is the internal one

Our services do not share a database or import each other's code. They integrate by API contract, which is a constraint we imposed on ourselves for testability — and it is the reason an external caller is not a special case. You get the contract our own execution service gets.

Contract-firstEvery request and response is a declared, versioned schema — not a convention
No shared stateServices integrate over the wire; you are one more caller, not an exception
Same failure semanticsVenue error codes map to one classified outcome, so retries mean the same thing everywhere
Per-client isolationEvery call is scoped to a client; funds never move between clients by construction

03

Contracts and reference data

live

One definition of what an instrument is, shared by every layer above it. This is the layer that makes the others comparable.

Instrument identity, coverage windows, and the bulk dump

Reference data is a service, not a file. It resolves an instrument to a canonical identity, carries the window over which data is expected to exist, and tells you where the archive for it lives. Venue lists and adapter keys live in the shared contracts package, so a venue means the same thing to every service.

Why identity is the hard part

The same economic instrument is spelled differently on every venue. A canonical identity is what lets a strategy say "this perpetual" once and have it resolve correctly across venues — and it is what makes coverage percentages comparable rather than a per-venue accounting curiosity.

Instrument record — the fields that travelSchema
class InstrumentRecord: instrument_id: str # canonical identity venue: str instrument_type: str # spot | perp | future | option | ... source_archive_url_template: str # where the archive lives coverage_start: date # when data is expected to begin coverage_end: date | None

Delivery: query for a single instrument, or take the whole universe as a parquet dump and join it locally.

04

The coverage model

live

The most important section in this document. How we state what we have, and — more importantly — how we state what we do not.

Honest coverage: four states, not two

A naive coverage number treats every missing file as a gap. That is wrong in a way that matters: a venue that did not exist in 2021 has no 2021 data, and counting that as a gap makes a complete dataset look broken while hiding the gaps that are real.

Capture statesEvery shard is in exactly one
StateMeaningCounts against coverage?
CapturedData is present and verifiedNo — this is the numerator
Expected, absentShould exist; does not. A real gapYes
Expected unattemptedIn scope, not yet fetchedYes — and it is the recoverable half
Not expectedVenue or instrument did not exist thenNo — excluded from the denominator
What this buys you

The distinction between expected-absent and expected-unattempted is the difference between "this data cannot be obtained" and "this data has not been fetched yet." The second is a schedule; the first is a limit. Most coverage conversations conflate them, and the conflation always favours the seller.

The denominator

Coverage is stated per (asset group × venue × instrument type × data type), and for on-chain venues also per chain. A single headline percentage across all of them would be an average over incomparable things.

pendingVenue-and-data-type pairs in scope
pendingCurrently captured
pendingObtainable without new sources
pendingGenuinely unavailable

These four figures are the spine of this document and will be measured from the availability manifest, not estimated. Until then they stay marked.

06

Getting the data

partial

Two modes, one availability model: ask what exists, then take it as a daily batch file or as a live stream.

Availability, batch download, and streaming

Ask first

Availability is a query, not a guess. You ask for a given asset group, venue, instrument type and data type over a date range, and get back what exists, in which capture state, at what granularity — before committing to a transfer.

Batch

Daily parquet, partitioned along the same axes the availability query uses, so the path you download is the path you asked about. Instruments come as a bulk parquet dump on the same model.

Live

Streaming, on the same schemas as batch. This matters more than it sounds: the live and batch paths are the same code, so a strategy developed against history behaves identically against a stream. That property is enforced rather than asserted — see readiness.

Why batch and live share schemas

If live data has its own shape, every consumer needs two implementations and they drift. Keeping one schema means a backtest and a live run read the same columns, and a discrepancy between them is a bug rather than an expected difference you learn to ignore.

08

The instruction contract

live

One envelope for every action, on every asset class. Swap, lend, transfer, stake, withdraw, back, lay — the same shape, the same lifecycle, the same audit record.

Why normalisation is the product, not a convenience

If you want a user to move from a conversational interface into an executable strategy, the hard part is not generating an idea — it is that every venue and asset class expresses actions differently. A unified instruction set is what makes that translation tractable: the interface emits one shape, and the number of things downstream has to understand does not grow with the number of venues.

The instruction envelopeContract
class StrategyInstructionEnvelope: action: InstructionAction # what to do instrument: InstrumentKey quantity: decimal reference_price: decimal # the benchmark it assumed execution_policy_ref: str # which policy governs it urgency: Urgency eligible_venues: list[str] venue_constraints: VenueConstraints
The design decision worth noticing

Strategy does not choose an algorithm. It states intent, a reference price, and an urgency, then names a policy by reference. Execution owns algorithm selection entirely. That is what allows execution to improve — new algos, new venues, better routing — without a single strategy changing.

The action vocabulary

ActionsOne vocabulary across asset classes
FamilyActionsApplies to
TradeBuy, sell, closeSpot, perps, futures, options
On-chainSwap, lend, borrow, repay, stake, unstakeDeFi protocols
EventBack, laySports and prediction venues
MovementTransfer, deposit, withdrawWallets, exchanges, custody

A caller that can express a buy can express a lay, or a stake, without new plumbing — only a different action on the same envelope.

09

Archetypes and registry scope

live

A strategy is an archetype plus configuration. Archetypes declare what they need through registry contracts, and the system checks those declarations rather than trusting them.

What an archetype is, and how new ones arrive quickly

An archetype is a reusable strategy shape — the structure of a trade family, independent of which instruments or venues it runs on. Configuration turns an archetype into a running strategy. The same archetype can be instantiated many times against different venues and parameters.

Subscription by registry contract

An archetype declares what it consumes — which data types, which feature groups, which venue capabilities — and that declaration is machine-checked. If an archetype needs a data type a venue does not carry, that combination is not offered rather than failing at run time.

Declared inputsEach archetype names the data types and feature groups it requires
Checked, not trustedA declaration that the data cannot satisfy is caught before it runs
Venue scopeArchetypes are offered only for venues whose capability record supports them
AdditiveA new archetype declares its needs and inherits the whole pipeline — no bespoke wiring
On what is not described here

This section covers archetype structure — how strategies are shaped, declared and scoped. It does not describe the parameters or signals that make any particular strategy profitable. That distinction is deliberate and is where the line sits.

10

The strategy wizard

partial

Configuration is the real surface area of a strategy platform. The wizard generates it — validated against the same schemas the services enforce — instead of asking anyone to hand-write it.

Guided configuration, and why it matters for an AI-driven front end

A strategy's configuration is long, typed, and interdependent: venues, instruments, sizing, risk limits, execution policy, slot identity. Written by hand it is error-prone; generated from a guided flow it is reproducible. The wizard walks the decisions in dependency order and emits a config that validates against the governing schema.

Why this is the natural bridge from a conversational interface

If your users describe intent in natural language, something has to turn that into a validated, executable configuration. The wizard is that step, and it is programmable — the same flow a human clicks through can be driven by an agent, because it is schema-validated at every stage rather than free-form.

Wizard stagesEach stage validates before the next unlocks
StageDecidesConstrained by
ArchetypeWhich strategy shapeWhat the archetype registry offers
UniverseInstruments and venuesVenue capability and data coverage
SizingCapital and position limitsRisk envelope
RiskDrawdown, leverage, exposure boundsGoverning limits
ExecutionPolicy reference and urgencyAvailable policies for the action set
IdentitySlot and deployment targetClient scope and isolation
The constraint that makes it useful

Each stage is constrained by the layers beneath it. You cannot select a venue whose data does not support the archetype, or an execution policy that does not apply to the actions the archetype emits. The wizard is not a form — it is the registry contracts made interactive, which is why its output is valid by construction.

12

Execution: routing and algos

partial

Execution decides how. It selects an algorithm from policy, routes to a venue adaptor, and can chain dependent steps into one sequence.

Three levels of depth — take as much as you need

Execution can be adopted at three depths, and they are genuinely separable. You do not have to take the smarts to get the connectivity.

Adoption depthsEach is a superset of the one above
DepthYou getSuits
1. ConnectivityNormalised routing to venue adaptors; one instruction shape, many venuesYou already have execution logic and want reach
2. AlgorithmsPolicy-selected execution algos rather than straight market ordersYou want execution quality without building it
3. SequencesChained dependent actions as one governed unit — borrow, then swap, then stakeMulti-step on-chain positions

Policy-driven algo selection

Algorithms are chosen by a versioned, content-hashed policy table gated on the instruction's action and urgency — not hard-coded per strategy. Changing execution behaviour is a policy change, and because policies are versioned, any fill can be traced to the exact policy that governed it.

Chained sequences

A multi-step position — borrow, swap, stake — is expressed as a sequence with dependencies rather than three unrelated instructions. The sequence is governed as a unit, so a failure partway is a defined state rather than an orphaned position.

Matching fidelity, and refusing rather than pretending

Execution knows what data granularity a venue actually supports. If a caller asks for a matching class the venue's data cannot serve, execution refuses rather than approximating — quietly matching as though tick data existed when it does not is how a backtest and a live run silently diverge.

Venue error handlingContract

Every venue's documented response and error codes map to one classified outcome — retry, reconnect, or fail — in a single registry keyed by venue and code. A venue's failure behaviour is therefore known before production, and a retry means the same thing on every venue.

13

Treasury, wallets, transfers

partial

Both halves are available: querying balances, and instructing movement. They are separable, and most integrations want the first before the second.

Balance visibility, transfer rails, and the isolation guarantee

Reading

Position and balance reading is a read-only surface by contract — the adapters expose balances, positions and account snapshots and have no order-placing or signing capability at all. That separation is structural, not a convention.

Moving

Transfers are expressed as instructions on the same envelope as trades, and route to a rail appropriate to the movement — exchange-internal, on-chain, or custody.

A guarantee worth stating plainly

Funds never move between clients. Every transfer is scoped to a single client identity and the code raises rather than executing a cross-client movement. This is enforced at the contract layer, not left to operational discipline.

Signing surfaces

Signing is pluggable — local keys, cloud-KMS-encrypted keys, or MPC custody providers — declared per deployment rather than assumed. Which surface is in use is part of the audit record.

Readiness: batch, paper, live

partial

Three modes, stated per venue rather than as a platform-wide claim. What separates them is which accounts exist, not which code exists.

The mode model and how readiness is derived
ModesA venue sits at the highest mode whose requirements all hold
ModeMeansNeeds
BatchResearch and backtest against history, honestlyNo venue credentials
PaperRuns forward without capital at risk. Either against a venue testnet, or simulated through our own matchingLive market data; testnet accounts where they exist
LiveReal capitalLive credentials and funded accounts
Readiness is computed, not declared

A venue's mode is derived from checks rather than written down, so it cannot drift as the system changes. Where a check does not yet exist, the venue reports unverified — never a pass. A readiness table that cannot say "I don't know" is not telling you anything.

Why batch and paper must agree

The same code path serves batch and live, and paper is compared against a batch re-run of the same window. If they disagree, that is a defect to fix rather than an expected difference — which is what makes a backtest result meaningful as a forward-looking claim.

Security and the audit record

partial

Treated as a prerequisite of delivery rather than a later hardening pass, because it is a control layer this has to satisfy regardless.

Isolation, immutability, and what the record has to answer
Client isolationPer-client scoping end to end; cross-client movement raises rather than executes
Immutable recordsPositions, trades, fills, orders and instructions are append-only; changes are audited status transitions
Credential handlingSecrets from a managed store, hot-reloadable, never in configuration files
Kill switchesScoped halts — all live, per archetype, or per venue — with defined resume paths

The question an audit record must answer

Not just what happened, but what was attempted. A cancel issued while an order was in flight and a cancel issued after confirmation are different events with different outcomes, and a record that cannot distinguish them cannot answer the question that matters after an incident.

Escalation

Failures resolve through a defined ladder rather than ad hoc alerting — retry, restart, drain, hold dependants, halt — with each step's scope declared. Automated recovery handles the classes it is allowed to; the rest escalates to a human with the reason attached.

The honest position on step 5
