    Research and backtest as a service — the backtest mirror

    For every engagement model above, the work starts the same way: we research and backtest the strategy for the client, not just review one they hand us. What makes that backtest worth trusting is that promotion to paper and live does not rewrite it — it runs the identical code path.

    The backtest mirror, precisely

    Promotion from backtest to paper to live is not a re-implementation at a higher fidelity — it is the same decision path (V2EngineOrchestrator.on_tick()), the same data types, the same execution assumptions, down to granular latency assumptions and book-triggered events. The platform's own determinism proof states this precisely: paper(W) must equal batch-rerun(W) trade-for-trade — any non-zero difference is treated as a bug, not a tolerance to absorb. The only intentional divergence left is the live fill boundary, where real venue slippage, fees and partials show up — and that live − paper delta is, by design, the execution-quality measurement, not noise.

    Source: /codex/09-strategy/operational/paper-batch-live-reconciliation.md — the determinism spine SSOT (ε=0 paper↔batch proof; live↔paper delta = execution alpha). See also §16 (the same-code-path guarantee behind it).

    We backtest both halves of the strategy, not just the signal: the decision logic, and the execution — the algo design (routing, sizing, aggression) is chosen against the client's own risk limits and to generate alpha in the execution itself, not just to fill the order (§12, in depth at §30). Once that mirror is proven, taking the strategy live means moving it onto the same infrastructure that produced the backtest — not a migration to a different execution stack.

    Contracts and reference data

    partial✓ verified owner: instruments_master

    One definition of what an instrument is, shared by every layer above it. This is the layer that makes the others comparable.

    Instrument identity, coverage windows, and the bulk dump

    Reference data is a service, not a file. It resolves an instrument to a canonical identity, carries the window over which data is expected to exist, and tells you where the archive for it lives. Venue lists and adapter keys live in the shared contracts package, so a venue means the same thing to every service.

    Why identity is the hard part

    The same economic instrument is spelled differently on every venue. A canonical identity is what lets a strategy say "this perpetual" once and have it resolve correctly across venues — and it is what makes coverage percentages comparable rather than a per-venue accounting curiosity.

    Glossary — the two words that carry the most weight

    Venue"Whose price is this." A price-source identity — deliberately decoupled from whether we can trade there. A separate predicate answers executability
    Asset groupCeFi, DeFi, TradFi, sports, prediction. The five worlds the same contracts span
    Instrument IDA canonical identity built by one dispatcher for every asset group, so the same thing has the same name everywhere

    Venue is broader than "exchange", deliberately. It can be a centralised exchange, a bookmaker, a prediction market, a data aggregator, a meta-broker, or a lending protocol on a specific chain — DeFi venues carry the chain in the identity itself (AAVE_V3-ARBITRUM, LIDO-ETHEREUM), because the same protocol on two chains is genuinely two venues.

    Why venue is defined by price, not by tradability

    A venue is a declared price source whether or not we can act on it. Executability is a separate predicate. That split matters: a book we cannot trade is still a legitimate member of the data universe and still improves a fair-value estimate — and conflating the two would either delete useful prices or imply we can trade somewhere we cannot.

    Canonical instrument IDs — one builder, five asset groups

    There is a single dispatch point for instrument identity across every asset group. The consequence is the part worth caring about: whatever you pull, you get a normalised identity, so the same underlying thing carries the same name regardless of which world it came from.

    # CeFi / DeFi / TradFi — venue, instrument type, symbol VENUE[-CHAIN]:INSTRUMENT_TYPE:SYMBOL BINANCE-SPOT:SPOT_PAIR:BTCUSDT AAVE_V3-ARBITRUM:LENDING:USDC # chain rides in the venue token CME:FUTURE:ES-20260320 # dated derivatives append the expiry

    DeFi token symbols preserve on-chain case (aUSDC, stETH) because that case is meaningful on chain; CeFi and TradFi symbols are uppercased. Dated derivatives append -YYYYMMDD, and options add strike and side.

    The example worth dwelling on

    Event markets are where normalisation earns its keep. The same real-world outcome, quoted on a sports exchange and on a prediction market, resolves to two IDs that differ only in the venue token:

    FOOTBALL:BETFAIR_EX_UK:MATCH_ODDS:EPL:2025-26:ARSENAL-CHELSEA::HOME FOOTBALL:POLYMARKET:MATCH_ODDS:EPL:2025-26:ARSENAL-CHELSEA::HOME

    Sport, market, league, season, fixture and selection are identical. Only the venue differs — so comparing venues is a group-by, not an integration project. That is a bookmaker and a prediction market, in two different asset groups, made directly comparable by construction.

    What this is used for today, and one honest boundary

    A cross-venue detector over Kalshi, Polymarket and Betfair is shipped and paper-proven end to end. It normalises every venue onto one YES-probability scale — including de-vigging Betfair's decimal back/lay odds — and scans venue pairs for a box. Kalshi joins that comparison at the probability layer: its native identity is a market ticker (KXBTCD-26JUN24-T95000) rather than the fixture grammar above, so it is normalised for comparison rather than sharing the same ID string.

    The boundary, stated rather than blurred: the two-line example above is a real, shipped code example. The equivalent "compare across venues by group-by" property is demonstrated for sports and prediction markets; for CeFi, DeFi and TradFi the same builder and the same ID shape apply, but we do not claim a live cross-venue arbitrage proof there.

    04

    The coverage model

    partial? check owner: W2, W3

    The most important section in this document. How we state what we have, and — more importantly — how we state what we do not.

    Honest coverage: more than two states

    A naive coverage number treats every missing file as a gap. That is wrong in a way that matters: a venue that did not exist in 2021 has no 2021 data, and counting that as a gap makes a complete dataset look broken while hiding the gaps that are real.

    Capture statesEvery shard is in exactly one
    State Meaning Counts against coverage?
    Captured Data is present and verified No — this is the numerator
    Attempted, failed Fetch was attempted; it failed or errored Yes — this is the real gap
    Expected, unattempted In scope, not yet fetched Yes — and it is the recoverable half
    Expected, confirmed empty Attempted; genuinely nothing there for this shard No — a confirmed absence is not a gap
    Not expected Venue or instrument did not exist then No — excluded from the denominator entirely
    What this buys you

    The distinction between expected-absent and expected-unattempted is the difference between "this data cannot be obtained" and "this data has not been fetched yet." The second is a schedule; the first is a limit. Most coverage conversations conflate them, and the conflation always favours the seller.

    The percentages below are pipeline coverage — declared capability that has actually reached instruments-service, then market-tick-data-service (raw capture), then market-data-processing-service (candle and derived computation), then features-service.     Strategy and execution are deliberately excluded from this percentage — not because they are unmeasured, but because a percentage there is meaningless. Both scale with configuration iterations and client count rather than a fixed declared universe: a client adding a fifth strategy config, or running forty live strategies instead of four, says nothing about coverage, and forcing a denominator onto either would manufacture a number shaped like the ones below without meaning the same thing.

    Getting the data

    partial✓ verified owner: W1

    Two modes, one availability model: ask what exists, then take it as a daily batch file or as a live stream.

    Availability, batch download, and streaming

    Ask first

    Availability is a query, not a guess. You ask for a given asset group, venue, instrument type and data type over a date range, and get back what exists, in which capture state, at what granularity — before committing to a transfer.

    Batch

    Daily parquet, partitioned along the same axes the availability query uses, so the path you download is the path you asked about. Instruments come as a bulk parquet dump on the same model.

    Why parquet

    Parquet is typed and columnar — the schema travels with the file, and compression is native rather than a wrapper you add yourself, so a day's shard is smaller on the wire and on disk than an equivalent flat file without losing type information at read time. That is the default, not a constraint: a caller who needs a different compression codec, or a flat CSV for a downstream tool that cannot read parquet, can ask for it — the underlying data does not change, only its serialisation on delivery.

    Live

    Streaming, on the same schemas as batch. This matters more than it sounds: the live and batch paths are the same code, so a strategy developed against history behaves identically against a stream. That property is enforced rather than asserted — see §16.

    Why batch and live share schemas

    If live data has its own shape, every consumer needs two implementations and they drift. Keeping one schema means a backtest and a live run read the same columns, and a discrepancy between them is a bug rather than an expected difference you learn to ignore.

    Source: market-tick-data-service/market_tick_data_service/api/routers/external.py's /delivery/stream route is backed by the UTL unified_trading_library.streaming.event_facade (get_transport) — the same facade the internal live-tick sink publishes through. Full parameter tables, worked requests and responses, and error codes for the availability and delivery endpoints are in §26.

    Keeping history current — continuous T+1 backfill

    History is not a one-time load. Every shard is stamped with an explicit cadence — a one-off backfill, a nightly T+1 daily run, a scheduled recurring pull, continuous live capture, or a recovery replay — tracked as its own manifest column, separate from which vendor served it. The nightly T+1 run is what keeps yesterday's data present today without a manual re-trigger: the same pipeline that backfills years of history also runs it one day at a time, on a schedule, so the corpus a strategy trains or backtests against never falls more than a day behind live.

    Source: manifest schema v9's cadence column ("one_off_backfill" | "t1_daily" | "scheduled_recurring" | "continuous_live" | "recovery_replay"), an axis orthogonal to pipeline_mode — one endpoint can serve both a nightly T+1 run and a long-term backfill under the same mode. /codex/02-data/availability-manifest-and-data-status.md.

    WebSocket reconnection — a stale window is flagged, never silently treated as fresh

    A live connector's socket drops and reconnects for reasons outside anyone's control — a venue-side bounce, a network blip. What matters is that a window built across a reconnect is never presented as though nothing happened: every venue connector tracks its own reconnect state, and the moment a reconnect occurs, the window it affects is stamped data_freshness=STALE rather than FRESH — a consumer reading the manifest can tell the difference without guessing from gaps in the data itself. A background heartbeat, independent of whether a window has actually closed, checks in periodically so a connector that is still "up" but has stopped producing ticks is caught by a stall detector rather than going quiet unnoticed. Separately, on the data-vendor side (Databento, The Graph and others queried over REST rather than streamed), API keys rotate across a pool per request, with a rate-limit hit on one key routing the next call to a different, non-limited key rather than stalling the whole feed on one exhausted credential.

    Source: market-tick-data-service/market_tick_data_service/live/_ws_window_helpers.py's WSFeedConnector.pop_reconnect_flag(); market_tick_data_service/live/websocket_runner.py's 60-second PipelineHeartbeatTimer stall watchdog; key-pool rotation in market_tick_data_service/market_interface/clients/thegraph_base_client.py and databento_base_client.py.

    Replaying data intraday (in development)

    Today's gap-fill mechanism re-drives historical sources back through the same live transport when the live pipeline itself loses data — a websocket disconnect that outlasts the reconnect grace period, an intraday VM restart — using a per-shard watermark to resume exactly where it left off rather than re-running the whole window. That mechanism is internal today. What is in development is exposing the same capability directly to a counterparty: the ability to replay your own already-delivered data for a given intraday window on demand, rather than waiting for the next scheduled batch. This matters most around an exchange outage — if a venue drops a connection or halts trading mid-session, pulling exactly the window that was missed, on your own schedule, is the difference between a clean recovery and reconstructing history by hand.

    Source: replay runner and per-shard replay_watermark handoff — /codex/05-infrastructure/replay-subsystem.md. Customer-facing exposure tracked in /plans/active/data_pipeline_completion_2026_08_21.md.

    The instruction contract

    partial✓ verified owner: W11

    One envelope for every action, on every asset class. Swap, lend, transfer, stake, withdraw, back, lay — the same shape, the same lifecycle, the same audit record.

    Why normalisation is the product, not a convenience

    If you want a user to move from a conversational interface into an executable strategy, the hard part is not generating an idea — it is that every venue and asset class expresses actions differently. A unified instruction set is what makes that translation tractable: the interface emits one shape, and the number of things downstream has to understand does not grow with the number of venues.

    Source: unified_api_contracts/internal/architecture_v2/schemas.py — the real, declared StrategyInstructionEnvelope family used by the external instruction endpoint in §02. That endpoint's full parameter reference, a worked request/response and its error codes are in §26.

    The StrategyInstructionEnvelope fields below, shaped as the body of the POST that carries them — field names and types are the real, declared contract; the request line is illustrative.

    ExampleShape of a real POST body — values illustrative

    reference_price is the benchmark strategy assumed; execution_policy_ref names which policy governs the instruction; reference_position is strategy's believed position per eligible venue; credit is strategy-owned — a band or a threshold; and position_adjustment_bps_per_unit_risk is a symmetric skew coefficient against raw position.

    The design decision worth noticing

    Strategy does not choose an algorithm. It states intent, a reference price, and an urgency, then names a policy by reference. Execution owns algorithm selection entirely. That is what allows execution to improve — new algos, new venues, better routing — without a single strategy changing.

    Reference position, credit, and per-position adjustment

    A generalisation of the reference-price idea above, extending it from "what did the market look like" to "does execution's view of the position match strategy's." reference_position states strategy's believed position per eligible venue, shaped like venue_constraints so it stays meaningful when the venue is not chosen until execution time (SOR_AT_EXECUTION routing); a mismatch on the venue actually used is an integrity check, not a market-move tolerance, and reuses the same four-outcome risk-consequence vocabulary (BLOCK/SCALE_DOWN/MONITOR/ TEST_ONLY) the preflight risk gate already supports elsewhere, defaulting to BLOCK. credit is strategy-owned and strategy-computed — a band around the reference price for market-making, a hard fire-or-don't threshold for arbitrage — execution only consumes whatever is cached. position_adjustment_bps_per_unit_risk is one symmetric coefficient against the raw, single-instrument, single-venue position, generalising the existing skew_on_inventory concept off market-making specifically. planned~ assumed — none of this is built yet.

    Archetypes and registry scope

    partial? check owner: W6

    A strategy is an archetype plus configuration. Archetypes declare what they need through registry contracts, and the system checks those declarations rather than trusting them.

    What an archetype is, and how new ones arrive quickly

    An archetype is a reusable strategy shape — the structure of a trade family, independent of which instruments or venues it runs on. Configuration turns an archetype into a running strategy. The same archetype can be instantiated many times against different venues and parameters.

    Subscription by registry contract

    An archetype declares what it consumes — which data types, which feature groups, which venue capabilities — and that declaration is machine-checked. If an archetype needs a data type a venue does not carry, that combination is not offered rather than failing at run time.

    Declared inputsEach archetype names the data types and feature groups it requires
    Checked, not trustedA declaration that the data cannot satisfy is caught before it runs
    Venue scopeArchetypes are offered only for venues whose capability record supports them
    AdditiveA new archetype declares its needs and inherits the whole pipeline — no bespoke wiring

    This section covers archetype structure — how strategies are shaped, declared and scoped. It does not describe the parameters or signals that make any particular strategy profitable. That distinction is deliberate and is where the line sits.

    Execution: routing and algos

    partial? check owner: execution_master

    Execution decides how. It selects an algorithm from policy, routes to a venue adaptor, and can chain dependent steps into one sequence.

    Three levels of depth — take as much as you need

    Execution can be adopted at three depths, and they are genuinely separable. You do not have to take the smarts to get the connectivity.

    Adoption depthsEach is a superset of the one above
    Depth You get Suits
    1. Connectivity Normalised routing to venue adaptors; one instruction shape, many venues You already have execution logic and want reach
    2. Algorithms Policy-selected execution algos — TWAP, VWAP, ICEBERG — rather than straight market orders You want execution quality without building it
    3. Sequences Chained dependent actions as one governed unit — borrow, then swap, then stake Multi-step on-chain positions

    Policy-driven algo selection

    Algorithms are chosen by a versioned, content-hashed policy table gated on the instruction's action and urgency — not hard-coded per strategy. Changing execution behaviour is a policy change, and because policies are versioned, any fill can be traced to the exact policy that governed it.

    Source: execution-service/execution_service/algorithms/registry.py maps algorithm IDs (TWAP, VWAP, ICEBERG) to their execution and config classes; a straight market order is the default when no policy names an algo.

    Chained sequences

    A multi-step position — borrow, swap, stake — is expressed as a sequence with dependencies rather than three unrelated instructions. The sequence is governed as a unit, so a failure partway is a defined state rather than an orphaned position.

    Matching fidelity, and refusing rather than pretending

    Execution knows what data granularity a venue actually supports. If a caller asks for a matching class the venue's data cannot serve, execution refuses rather than approximating — quietly matching as though tick data existed when it does not is how a backtest and a live run silently diverge.

    Venue error handlingContract

    Every venue's documented response and error codes map to one classified outcome — retry, reconnect, or fail — in a single registry keyed by venue and code. A venue's failure behaviour is therefore known before production, and a retry means the same thing on every venue.

    Position handshake — keeping strategy and execution in agreement

    A price moving away from what strategy last saw is normal — the market moved. A position disagreement is not: if execution's own record of what it holds on a venue differs from what strategy believes it holds there, the two services disagree about ground truth, not about a moving market, and that is worth treating differently. The design in progress has strategy state its believed position per venue alongside every instruction it sends, so execution can check its own live view against it on every instruction — not as a slow periodic reconciliation pass, but as an instant, per-instruction check reusing the same block/scale-down/monitor consequence vocabulary the risk engine already applies to any other triggered rule. Default behaviour on a mismatch is to block, because a strategy and its execution layer silently disagreeing about what is actually held is exactly the class of problem §21's reconciliation framework exists to catch, just checked faster and closer to the point of action.

    Design in progress, not yet shipped — reference_position has zero real consumers in execution-service today (confirmed 2026-08-22); the per-instruction check described above is the intended behaviour, not current behaviour.

    Fast-path repricing from a cached reference

    Re-running a strategy's full decision loop on every tick is too slow for some opportunities — a market-making quote, an arbitrage leg — to react to a market that has already moved by the time a fresh instruction round-trips back from strategy. The pattern being generalised across the platform: strategy periodically publishes a reference price and a sensitivity factor for how that opportunity's value moves with the market, and execution — watching the live feed directly, without waiting on strategy — cheaply extrapolates from the cached reference rather than recomputing from scratch, clamping to a defined staleness bound rather than extrapolating indefinitely. This is what makes HFT-grade reaction speed possible from a co-located or cross-region execution engine without every decision needing a fresh round-trip to strategy. It rides on the same discipline applied everywhere market data is captured: every observation carries both the exchange's own timestamp and the local time it was received, so a stale or slow-arriving update is provably distinguishable from a genuinely fresh one rather than assumed current.

    The extrapolation engine (DeltaProxyRepricer, QuoteMaintainer) is real, tested code; end-to-end wiring for the general contract is in progress — /codex/04-architecture/cross-domain-state-fabric.md. Dual-timestamp capture: unified_trading_library/domain_client/validation.py (local_timestamp — when we received it — validated against timestamp — the exchange's own clock).

    Security and the audit record

    partial? check owner: W15

    Treated as a prerequisite of delivery rather than a later hardening pass, because it is a control layer this has to satisfy regardless.

    Isolation, immutability, and what the record has to answer
    Client isolationPer-client scoping end to end; cross-client movement raises rather than executes
    Immutable recordsPositions, trades, fills, orders and instructions are append-only; changes are audited status transitions

    The question an audit record must answer

    Not just what happened, but what was attempted. A cancel issued while an order was in flight and a cancel issued after confirmation are different events with different outcomes, and a record that cannot distinguish them cannot answer the question that matters after an incident.

    Escalation

    Failures resolve through a defined ladder rather than ad hoc alerting — retry, restart, drain, hold dependants, halt — with each step's scope declared. Automated recovery handles the classes it is allowed to; the rest escalates to a human with the reason attached.

    The same discipline applies one layer up, to the platform's own software delivery. A build or test failure is detected automatically, dispatched to an agent that diagnoses the root cause against the actual failing logs — not a guess — applies a fix, and ships it back through the same quality gates every other change goes through, verified green before it lands. A failure that cannot be resolved this way escalates to a human with the diagnosis already attached, rather than sitting silently red. This is not a roadmap description: the fix behind several of the items on this page reached production through exactly this path.

    Inter-service SLAs and disaster recovery

    Every cross-service check that matters declares its own cadence rather than sharing one global assumption. Reconciliation (§21) runs a defined nightly pass with a separate, faster path for an operator-driven break; per-input staleness (§24) is bounded per input, not platform-wide; kill-switching (keypoints above) is scoped and immediate rather than all-or-nothing. Disaster recovery follows the same standing-standby model for the infrastructure behind it: the orchestration and delivery infrastructure that keeps the platform's own engineering running keeps a documented, previously-live standby on a second cloud provider — stopped rather than torn down — with an exact, already-written recovery procedure to bring it back to serving traffic, rather than an improvised response written after the fact.

    Cloud-agnostic infrastructure

    Storage and compute are addressed through one provider-neutral interface rather than one cloud's SDK called directly — every bucket is resolved by name through a single resolver rather than a hardcoded path, already spanning both AWS and GCP in production today. A third provider (IONOS) is being brought into the same pattern now, and the point of building it this way is that adding a provider is a configuration change to the resolver, not a rewrite of every service that touches storage — the same shape extends to Azure on request. In practice this also means a deployment can run compute and streaming in the cloud region nearest a client, and stream across clouds within that same region into the client's own account — keeping data close to where it is used and avoiding cross-region egress cost.

    Source: unified_trading_library/cloud_interface/bucket_naming.py's resolve_bucket_name(); provider duality — /codex/05-infrastructure/bucket-isolation-model.md, /codex/05-infrastructure/cloud-agnostic-script-pattern.md.     Dual authorization on treasury movements

    A withdrawal is not a single signature away from moving funds. The number of independent, HMAC-signed approvals required scales with the client's configured tier — SMALL needs 1, MEDIUM needs 2, LARGE needs 3 — accumulated server-side until quorum is reached; a duplicate approval, or one submitted after quorum is already met, is rejected outright rather than silently accepted.     Latency, preflight, and staleness SLAs

    planned? check owner: W16

    Two failure modes matter more than most: a strategy that starts without everything it needs, and one that cannot tell how stale its inputs are. The target design closes both, and fails closed by default.

    Registration-time checks, not runtime surprises
    Triggers named explicitlyWhat a strategy reacts to and when — time-based or event-based, normally a subscription to a broadcast stream rather than a poll
    Latency tracedEvery artefact records when its data was received and when it was sent, so a slow leg is attributable rather than inferred
    Preflight at registrationA strategy missing a required input fails registration, not a live run — the expensive way to learn it is discovering it mid-run
    Per-input staleness SLAA defined reasonable wait before a given input is treated as stale, named per input rather than assumed platform-wide
    RULED — missing or stale data fails closed by default

    Every strategy is considered startup-ready only once it has fresh data across everything it needs — position, PnL, risk, the specific venues it trades, and every market-data input it consumes — checked for both presence and freshness. Absent or stale fails closed by default; any deliberate fail-open exception has to be stated and justified per input, not left as an unhandled gap that happens to proceed.

    This is specified, not built. No trigger, latency-tracing or staleness-SLA mechanism described here is live today.

    The external execution API — two ways to run it

    planned? check owner: W22

    §02 documents strategy-service's real counterparty-facing surface — the signal-leasing API. This section is a different gap: automating strategy's own trading decisions into execution instructions internally, without a human or an external system relaying them by hand. Not a new integration pattern; the same instruction envelope and execution path already documented in §08 and §02, exposed across a process boundary two different ways.

    Internal messaging, an external transport, and who hosts what
    The honest state today

    A workspace-wide search found no internal messaging — Pub/Sub or otherwise — connecting strategy-service's decisions to execution-service today, and no direct API client between them either. The only live instruction path is the manual one: ManualOperationHandler → LiveOrchestrator.execute_instruction() (§02) — not an automated strategy-to-execution bridge. Closing that gap is the first part of this work, not an assumed foundation.

    Internal: messaging, not a service dependency

    Strategy's decisions reach execution the same way market data already does (§16) — over the UTL EventTransport facade, Pub/Sub-backed, keyed on what the subscriber needs. Two subscriptions, not one: execution subscribes to strategy's instruction stream, and separately to the feature groups it needs from features-service. A messaging dependency in both cases, never a direct service-to-service call — this platform holds that boundary everywhere else, and this is no exception.

    Every instruction is sinked for audit, one by one

    Every strategy-emitted instruction lands in GCS through the same shard-and-manifest pipeline the rest of this platform's data uses, queryable via BigQuery external tables — an audit and analysis surface, not only a live queue. Market tick data feeding the decision is aggregated separately (§04–§07); this sink is instructions only.

    Three deployments, one schema, different protocols

    Deployment topologySame StrategyInstructionEnvelope, different transport
    Deployment Serves Protocol
    Internal Our own strategy-service instructions Pub/Sub — low latency, our infrastructure
    External, automated Registered external clients' strategy instructions HTTP or WebSocket, latency-dependent — hosted on our side, callers known and allow-listed
    Manual DART, an external trading UI, or a manual API caller HTTP — manual trading has no latency floor to defend
    Two ways to run it, for an external client specifically

    We host it — a client sends strategy instructions to an execution-service deployment we run and maintain, registered and allow-listed on our side. They host it — the same execution-service image, Dockerized, config-driven, deployable on their infrastructure or ours, with the same hot-reload configuration model documented in §11. The call shape is identical either way — only who operates the deployment differs.

    What this needs from the instruction contract

    The action vocabulary (§08) has to grow past trade / on-chain / event / movement to cover control instructions — a scoped kill-switch and a flatten-position instruction, both already conceptually present as system behaviour (§15) but not yet expressible as an instruction a caller can send. Broker and routing configuration does not need a new field: venue_constraints on the envelope (§08) is already general enough to carry it, once populated.

    Extensibility — the grounded version of "we can build it"

    Every algorithm above — and the ones not detailed here (VWAP, Iceberg) — implements the same three-method contract: ExecutionAlgorithm.execute(), get_child_orders(), validate_config() (execution-service/execution_service/algo_library/base_algorithm.py).     That is the grounded version of "anything to improve latency, we can build": a new execution style is an implementation against a known, machine-enforced interface, not a platform rewrite. It does not make every future algorithm free — the wiring gap above shows two real implementations still sitting unconnected — but it is an architectural fact about the shape of the extension point, not a promise about turnaround time.
