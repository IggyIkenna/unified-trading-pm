    What this platform is

    One canonical platform spanning five market ecosystems — centralised crypto, decentralised finance, traditional markets, sports and prediction markets — with historical batch delivery and near-real-time streaming over the same canonical contracts, a controlled path from backtest through paper to live, and modular choices over who owns the signal and who owns execution.

    Five asset groupsCeFi, DeFi, TradFi, sports and prediction markets are represented through common discovery and data contracts — most providers expose a separate schema and operating model per domain.
    Live plus batchThe same canonical universe supports daily persisted delivery, replay/recovery and near-real-time consumption — research historically and operate live without rebuilding the integration.
    Lifecycle continuityBacktest, paper and live retain the same strategy/configuration identity and can be reconciled against each other — promotion is controlled and evidential, not a rewrite.
    Modular responsibilityA counterparty can own signals, execution, or both — the platform supports managed, licensed and infrastructure-only products without exporting core implementation.

    Subject to entitlement, a counterparty on this platform can:

    • Invest through our investment-management platform — allocations facilitated in both SMA (separately managed account) and fund structures.
    • Discover available instruments, venues, data types and historical coverage across all five asset groups.
    • Download point-in-time instrument catalogues and historical market data in bulk, for local research and recovery.
    • Consume near-real-time normalised market-data envelopes over a durable, replayable stream.
    • Lease an entitled signal slot at an agreed payload depth, receive it by pull or push, and acknowledge delivery.
    • Submit target-position, quote, cancel, transfer, DeFi and multi-leg instructions for execution where authorised.
    • Run an externally generated strategy through this platform's data, execution and reporting.
    • Inspect positions, NAV, P&L, attribution, trades, transfers and fees, scoped to their own client_id.
    • Promote a versioned strategy from backtest to paper to live under explicit approvals, limits and kill switches.
    Read this before treating any of the above as uniform across the five groups

    A common asset_group parameter proves architectural reach, not equal production coverage. Availability and execution capabilities are venue-, dataset-, action- and environment-specific — see the measured capability endpoints in each section below, and the coverage narrative in platform-external-api-walkthrough.html for the full picture per asset group.

    Rate limiting — a per-tier token bucket, keyed off subscription_tier, built on both routers

    ✓ verified Every endpoint on instruments-service's and market-tick-data-service's external routers now calls enforce_rate_limit(auth) before its own entitlement check. Mechanics mirror strategy-service's signal-leasing RateLimiter (§26) — a lazy, wall-clock-refilled token bucket, one token consumed per allowed call, never raising — but each service ships its OWN local implementation (no service→service import). The bucket is keyed per org_id, sized by the caller's CURRENT subscription_tier resolved fresh on every call (a tier change takes effect on the next request, no restart). Internal/S2S callers (auth.is_internal) bypass entirely — same precedent as the entitlement seams above. An exhausted bucket responds 429 with a Retry-After header (whole seconds, a conservative estimate of when the next token is available) rather than a bare rejection.

    Signal-leasing API — strategy-service

    The Signal Leasing surface is the outbound stream of the platform's own StrategyInstructionEnvelope emissions (strategy-service's polymorphic v2 instruction schema — TradeInstruction, SwapInstruction, LendInstruction, and siblings), delivered to a counterparty at their entitled payload depth: pull it via REST or receive it pushed to your webhook, then acknowledge it. strategy-service/strategy_service/signal_broadcast/ (15 modules: router.py, transport.py, emitter.py, credentials.py, audit.py, broadcaster.py, config.py, config_reloaders.py, envelope_projection.py, live_publish.py, failure_isolation.py, observability_ingest.py, observability_readers.py, observability_stores.py, __init__.py) plus the schema layer in unified-api-contracts/unified_api_contracts/internal/domain/signal_broadcast/ (counterparty registry, entitlements, rate limits, payload envelope) is built and wired end-to-end, source to acknowledgement.

    Complete surface — activation is a per-counterparty onboarding step

    ✓ verified Emission source: GroupBRunner (the same paper/live tick runtime every archetype runs through) forwards every emitted StrategyInstructionEnvelope to a signal_broadcast_publisher seam (engine/backtest/runner.py:213,271-272) wired at the real, CLI-reachable --operation paper-run call site (cli/handlers/paper_run_handler.py, via signal_broadcast/live_publish.make_signal_broadcast_publisher). Depth-filter projection: signal_broadcast/envelope_projection.base_payload_from_instruction() maps the real envelope (direction, reference/stop/take-profit prices, deadline, archetype identity) onto the base_payload shape SignalRouter.build_payload() already projects to MINIMAL/STANDARD/RICH per counterparty entitlement — the same depth-projection code the 6 endpoints below serve from.

    ✓ verified Activation is a config row, not a code change: Counterparty.status is the sole gate (is_counterparty_active(), counterparty.py:71) — transport.py's _authenticate() checks it before anything else and entitled_slots_for() returns an empty set for a non-ACTIVE counterparty. The registry's CounterpartyEntitlement.active_from/ active_to fields exist solely for billing/audit provenance (per the registry module's own docstring) — nothing in the module or its callers reads the clock and compares against them; no scheduled cutover flips a counterparty live. unified_api_contracts/internal/domain/signal_broadcast/registry.py currently seeds two staging counterparties (counterparty-stub-1, STANDARD depth, default rate-limit profile; counterparty-stub-2, MINIMAL depth, minimal rate-limit profile) with real webhook URLs + Secret Manager references injected at deploy time by deployment-service. Onboarding a counterparty is flipping its status to ACTIVE and provisioning its endpoint — the same registry-row step every counterparty in production goes through, not a platform gap.

    Authentication — distinct from §01

    Every route in this section sits behind its own auth, separate from the shared create_api_auth dependency the rest of this page uses. A caller sends Authorization: Bearer <jwt>; the JWT is HS256-signed and is verified against a per-counterparty HMAC secret — not a service-wide secret — resolved via CounterpartyCredentialsManager (credentials.py), which wraps the UTL ApiKeyReloader and hot-reloads each counterparty's secret from Secret Manager on a timer (default 300s) so a rotated secret propagates without a restart. Audience and issuer are also checked (config.jwt_audience / config.jwt_issuer).
